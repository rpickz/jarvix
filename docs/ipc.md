# Jarvix IPC protocol

## Transport

- **Socket:** `$XDG_RUNTIME_DIR/jarvix.sock`, mode `0600`. No TCP listener
  exists.
- **Framing:** newline-delimited JSON (one JSON document per line).
- **Protocol:** JSON-RPC 2.0. Clients send requests; the daemon sends
  responses, plus **notifications** (no `id`) for asynchronous events, pushed
  to every connected client.

A stale socket left by a crashed daemon is detected (connect fails) and
replaced on startup; a live socket makes a second daemon refuse to start.

## Versioning

`status.get` returns `protocol` (currently `1`). Incompatible protocol
changes bump it; clients should check it once after connecting. Additive
changes (new methods, new events, new fields) do not bump the version —
clients must ignore unknown events and fields.

## Requests

| Method | Params | Result | Notes |
|---|---|---|---|
| `session.start` | — | `{session_id}` | Cancels any active session first (interruption) |
| `voice.start` | — | `{}` | Idle → Listening; starts capture |
| `voice.stop` | — | `{discarded}` | Listening → Transcribing; transcription runs async. `discarded: true` means the capture was shorter than `audio.min_recording_ms` and the session ended quietly (`session.cancelled`) — skip the follow-up `session.submit` |
| `session.submit` | `{text?}` | `{}` | With `text`: skip audio, go think. Without: proceed when the transcript lands |
| `session.text` | `{text}` | `{session_id, confirmation, approved?}` | One typed turn, for a client with a text field (the conversation window's composer). Composes `session.start` + `session.submit {text}` — the `jarvix ask` path — but decides between them and a pending confirmation **in the daemon**, under one lock: with `awaiting_confirmation` in force the text answers the confirmation (`confirmation: true`, `approved` being the same reading a spoken yes/no gets) and the waiting session is left alone; otherwise a new session starts, cancelling any session in flight. Text that is empty or whitespace is rejected with `-32602` and starts nothing. Do not sequence `session.start` yourself from a text field: the state you read can go stale in the round trip, and starting a session then abandons the confirmation the user was answering |
| `session.cancel` | — | `{}` | Stops everything; no-op when idle |
| `session.confirm` | `{approved?}` | `{approved}` | Answers a pending tool confirmation (`approved` defaults to `true`); errors when nothing is pending or a voice reply is already being captured |
| `speech.cancel` | — | `{stopped}` | Stops spoken output whenever audio is actually playing, whatever the session state — mid-answer tool rounds included (issue #54). Stopping speech ends the turn (`tts.finished {interrupted: true}` when the answer had started speaking, then `session.finished`); a pending tool confirmation is abandoned as declined. `stopped: false` reports that nothing was playing — a no-op, not an error |
| `conversation.reset` | — | `{}` | Forget carried-over context (and any remembered tool approvals); the next turn starts a fresh thread. With retention on (ADR 0027) the old thread is already archived — turns are appended as they complete — so the reset only detaches it; it stays listed and reopenable. A session in flight is deliberately left alone — use `conversation.new` for the user-facing "new chat". Publishes `conversation.changed {reason: "reset"}` |
| `conversation.new` | — | `{}` | The explicit end of a conversation (issue #117, ADR 0038) — the one verb every New Chat surface is a thin client of: `jarvix new`, the window's New chat button, the bar menu item (the spoken "start a new conversation" intent reaches the same engine path from inside its own session). `conversation.reset` plus: a session in flight is cancelled first, and its exchange is committed **marked interrupted** into the thread being ended — archived and searchable, never dropped. The next utterance starts a fresh thread. Publishes `session.cancelled` (when a session was running) then `conversation.changed {reason: "reset"}` |
| `conversation.get` | — | `{turns, state, session_id, confirmation?}` | Snapshot of the current conversation for display: `turns` is an array of `{role, text}` (`user`/`assistant`, oldest first, including the in-flight user question once transcribed). A **resolved** tool confirmation is a turn of its own (issue #118): `{role: "confirmation", text, confirmation: {tool, command, rule?, outcome, source?, timeout_sec?}}` — `text` is the spoken question, `command` is verbatim (ADR 0014), `outcome` is `approved`, `declined`, or `timed_out` (never conflated), and it sits at the position the exchange happened, so a reopened window renders it as the static resolved card. Render it on open, then live-append from `assistant.delta` / `transcript.final` / `state.changed` / `error` events. `confirmation` is present only while a tool confirmation is pending: `{tool, command, summary, rule, timeout_sec, deadline_ms?}` — the same facts `tool.confirmation_required` / `tool.confirmation_deadline` carried, so a window opened *during* the wait can render the confirmation card (question, verbatim command, countdown) without having seen those events (issue #76). `deadline_ms` is absent while the question is still being spoken |
| `conversation.list` | — | `{retention, active_id, conversations, unreadable}` | The archive (ADR 0027), newest first: each `{id, started, last_active, turns, preview}`. Metadata only — no transcript is opened, so a large library lists fast. `unreadable` (`{id, error}` each) names conversations that could not be parsed: one bad file never hides the library, or itself. `retention: false` means `conversation.retention = "off"` — nothing new is being archived, but the listing (and deletion) still work. `active_id` is the conversation the live thread belongs to, `""` when none. Read-your-acknowledged-writes: a turn whose `session.finished` has been published is already in the listing — and reflected in `active_id` — by the time any `conversation.*` read issued afterwards answers; the daemon flushes the archive before reading, never the other way round (issue #115) |
| `conversation.read` | `{id}` | `{id, started, last_active, preview, turns}` | One whole archived conversation, read-only: `turns` is an array of `{role, text, ts}` (RFC 3339), oldest first. A turn from an exchange the user cut off also carries `interrupted: true` (issue #117); its text ends in the bracketed annotation the record was committed with, so clients need no special rendering. A confirmation record turn (issue #118) carries `confirmation: {tool, command, rule?, outcome, source?, timeout_sec?}` with `role: "confirmation"` — the same structured record `conversation.get` serves, at its archived position between the turns of its exchange. Unknown or unreadable ids are `-32602` |
| `conversation.search` | `{query, limit?}` | `{retention, active_id, results, searched, skipped}` | Full-text search over the archive, live head included (ADR 0028) — including a turn that finished the instant before the query: `session.finished` published means the exchange is findable, and `current` on its hits truthful (issue #115). `results` is ranked best first — exact phrase beats scattered words, recency breaks ties — each `{id, turn, role, ts, passage, current}`: `turn` is the 1-based position in that transcript, `passage` the matched text clipped to one line, `current` true when the hit is in the active conversation ("earlier in this conversation"). `limit` caps results (default 10, ceiling 20). `searched` counts conversations scanned; `skipped` (`{id, error}` each) names ones that could not be — the listing's unreadable contract. A blank query is `-32602`. The window's search box and `jarvix conversations search` are thin clients; the model's `conversations.search` tool shares the same searcher. Queries and passages are never logged |
| `conversation.open` | `{id}` | `{id, turns}` | Reopens an archived conversation as the active thread — the explicit action. The engine keeps the most recent `history_turns` exchanges as model context (the archive keeps everything the prompt cannot), restarts the follow-up window, and appends follow-up turns to the same record. Publishes `conversation.changed {reason: "opened", conversation_id}` |
| `conversation.delete` | `{id}` or `{all: true}` | `{deleted}` | Removes conversations from disk — files gone, no tombstones. Deleting the active conversation (or `all`) also resets the live thread, so the next turn cannot rebuild the record from working memory. Unknown ids are `-32602` |
| `context.last` | — | `{captured, session_id?, at?, age_sec?, duration_ms?, sources?}` | The desktop context gathered for the most recent question that reached the model (ADR 0019) — the audit surface behind `jarvix status --last`. `captured: false` means nothing has been gathered yet this daemon lifetime. Each source is `{source, text, chars, truncated, redacted}`: `text` is **exactly what the model was sent**, already capped at `context.max_chars` and already replaced by `[looks like a secret — not shared]` if it matched the secret heuristics; `chars` is the pre-truncation length. Retained in memory only — never persisted, never surviving a restart |
| `memory.last` | — | `{enabled, injected, session_id?, facts?, trimmed?, searchable?, total?, est_tokens?}` | The remembered facts injected into the most recent question that reached the model (ADR 0025) — the memory half of `jarvix status --last`, beside `context.last`. `enabled: false` means `memory.enabled = false`; `injected: false` means no turn has consulted the knowledge base yet this daemon lifetime. `facts` is what the model was actually given — each in the `memory.list` fact shape — `trimmed` how many *ambient* facts the token cap left out of the block (never out of storage), `searchable` how many facts were deliberately not offered to the block at all (the unpinned rest under ADR 0037's split — reachable through the `memory.search` tool, not a loss), `total` the store size at injection time, `est_tokens` the block's estimated cost. Retained in memory only |
| `memory.list` | `{query?}` | `{enabled, path?, count?, max?, warning?, facts?}` | The store itself, straight from disk (hand-edits included): every remembered fact, or those matching `query` (case-insensitive substring or shared significant word), most recently confirmed first. Each fact is `{id, content, stored, updated, pinned, source?, times_retrieved?, last_retrieved?, last_retrieved_spoken?, previous?}`: `pinned` is the ambient flag (#104); the retrieval stats appear **only for facts `memory.search` has actually returned** — a never-retrieved fact carries no stats keys, so no client can render a fabricated zero — and `last_retrieved_spoken` is the feeds' shared spoken wording ("four minutes ago"), one scale for every surface. The supersede trail (`previous`: `{content, stored, superseded}` each) answers "when did that change". `warning`, when present, is the book's over-budget sentence (a pinned set past `memory.max_injected_tokens`, or an unpinned book that outgrew it): the Memory tab and `jarvix memory list` show it verbatim — a trim is never silent (ADR 0037). `path` names the file — it is the user's to edit; `count`/`max` report the store cap. `jarvix memory list` is a thin client |
| `knowledge.status` | — | `{enabled, path?, fingerprint?, feeds?}` | The feed cache (ADR 0031): one entry per configured `[[knowledge.feeds]]` table — `{name, mode, enabled, interval_sec, ttl_sec, inject, has_value, stale, failing, value?, fetched?, age_sec?, age_spoken?, failing_since?, attempts?, last_error?}` — in declaration order. `age_spoken` is the shared spoken-style wording ("four minutes ago") so no client invents its own scale; `fingerprint` is the config file's, for `knowledge.set_enabled`'s external-edit check. `value` travels here deliberately (the user's own data over their own 0600 socket, the `memory.list` precedent) and nowhere else: logs and events carry names and counts only. `jarvix doctor` composes its "N fresh, M failing since …" line from this. Feed definitions remain plain `[[knowledge.feeds]]` TOML, and since #100 the window creates, edits, and deletes them through the generic entry-form verbs (`config.get_entry` … `config.delete_entry` with `family: "knowledge.feeds"`) beside the `enabled` switch and the manual refresh |
| `knowledge.refresh_now` | `{name}` | `{started}` | Fetches one feed immediately, through the exact scheduled-fetch path: same runner, same single-flight latch per feed (a refresh during an in-flight fetch is that fetch, not a second command), same gate identity — `knowledge.refresh` must resolve to allow, exactly as the scheduler requires. Asynchronous: the reply acknowledges the start, and completion arrives as `knowledge.updated`. Unknown, disabled, or gate-refused feeds are `-32602` with the reason |
| `knowledge.set_enabled` | `{name, enabled, fingerprint?}` | `{fingerprint, applied, reason?}` | Parks or resumes one feed, persisted into config.toml through the surgical entry editor: only that entry's `enabled` key changes — comments and sibling entries byte-preserved — the result is validated whole before anything is written, the write is atomic, and the running scheduler drops/readopts the feed on the same reload path hand edits use. A `fingerprint` (from `knowledge.status` or `config.get`) that no longer matches the file is a `-32002` conflict carrying the fresh fingerprint — hand edits are never clobbered. `applied: false` with `reason` means written but pending (a session was busy), the `config.set` contract. A disabled feed keeps its last cached value, is listed with `enabled: false`, and nothing fetches or injects it |
| `memory.forget` | `{id?}` or `{query?}` | `{forgotten, fact?, matches?}` | Deletes one fact from disk — trail and all; deletion is deletion. By `id`, or by `query` when it matches exactly one fact; several matches delete **nothing** and come back as `matches` for the caller to pick an id from (the same refuse-to-guess rule the model-facing tool follows). An unknown id is `-32602`; so is calling it with memory disabled |
| `memory.forget_gated` | `{id}` | `{session_id}` | The window's per-fact Forget (#92): starts a session that runs the `memory.forget` tool identity through the permission gate, so the standard confirmation card appears naming the exact fact — resolved from the store, never from the caller — and only an approval deletes, through the registry with the ordinary `tool.*` audit events. Where `memory.forget` above is the CLI's deliberate direct line, this is the path for a button in a listing. An unknown id is `-32602` and no session starts |
| `memory.add` | `{content, pinned?}` | `{fact, warning?}` | The Memory tab's Add (#100): stores one new fact through the memory book's own write path — the same discipline `memory.remember` writes with (id assigned from the never-reused high-water mark, timestamps set, atomic fsync-and-rename). **Ungated**, per ADR 0025's reversibility split: typing a fact into the form is the user's explicit word, exactly like a spoken "remember that …", and a wrong add is undone with one forget. `pinned: true` (#104) creates the fact ambient in one save. Empty content is a `-32001` refusal with `problems: [{field: "content", message}]` — the entry-form wire shape, so the window's dialog code is shared — and a store at `memory.max_facts` is a `-32001` whole-entry problem; both write nothing. `warning` carries the book's near-cap sentence when the store is filling. Publishes `memory.entry_changed` |
| `memory.update` | `{id, content, pinned?}` | `{fact}` | The Memory tab's Edit (#100): supersedes one fact's text through the book — the old value moves onto the fact's `previous` trail with both timestamps, so nothing is destroyed and "when did that change" stays answerable, which is what makes this verb safe ungated (Forget, the destructive one, keeps its confirmation card). Since #104 the form sends `pinned` alongside the content and the daemon compares before writing: unchanged text with a toggled pin changes only the pin — no revision of identical wording is ever manufactured — and unchanged everything writes nothing. Refusals share `memory.add`'s shapes: empty content is field-keyed `-32001`, an unknown id is `-32602` naming it, and nothing is written on any refusal. Publishes `memory.entry_changed` |
| `memory.set_pinned` | `{id, pinned}` | `{fact, warning?}` | The fact card's one-click pin toggle (#104): marks or unmarks one fact as ambient through the book — timestamps and trail untouched, because a pin is presentation-of-memory state, not content. **Ungated** for the reversibility reason add and edit are: the opposite click undoes it exactly. `warning` carries the book's over-budget sentence when the new pin state creates one, so pinning past the budget answers with its consequence. An unknown id is `-32602` naming it. Publishes `memory.entry_changed` with action `pinned`/`unpinned` |
| `status.get` | — | `{state, session_id, version, protocol, ptt, policy, warm, wake, wake_state, last_timings, last_typing, conversations, prompt_budget}` | `ptt` is `"daemon"` when jarvixd watches the hold-to-talk chord itself (keybinding toggles must then no-op) or `"external"` when keybindings drive activation. `policy` is the effective tool permission policy: `{default, confirm_timeout_sec, remember_for_conversation, tools: {name: decision}}`. `warm` lists the supervised engine workers (ADR 0018), one entry per engine: `{name, running, pid, rss_mb, uptime_sec, restarts, last_error}` — empty when `performance.warm_engines` is off. `wake` is the background-listening report described under `wake.status` below, and `wake_state` is the one word the microphone indicator draws (`off`, `armed`, `muted`) — both included here so a client that connects mid-life gets the indicator right from one call rather than waiting for the next `wake.changed`. `last_timings` is the most recent `session.timings` payload (plus its `session_id`), or `null` before any session has finished; `jarvix status --last` prints it, alongside the desktop context from `context.last`. `last_typing` is the most recent `typing.audit` payload, or `null` when typing is off or nothing has been typed since the daemon started — it never carries the typed text. `conversations` is the archive-search state (ADR 0028): `{retention, archived, search}` — `search` is `"active"` or `"inactive"` (retention off with nothing archived), a state rather than a failure. `prompt_budget` is what one turn sends before the user has said a word (issue #71), estimated at bytes/4: `{system_prompt_tokens, tool_schema_tokens, memory_tokens, context_tokens, headroom_tokens, floor_tokens}` — measured from the daemon's composed system prompt and its actually-registered tool schemas; `jarvix status` prints the floor against the context window ollama reports serving, and `jarvix doctor` warns when the window is below it |
| `wake.mute` | `{muted?}` | the `wake.status` report | Closes or reopens the background microphone (ADR 0024). `muted` defaults to `true` — `jarvix mute` is the point, and unmuting is the explicit case. **Muting is synchronous**: the call returns only once the capture process has been killed and reaped and every audio buffer has been wiped, so the report it answers with is a statement of fact. Unmuting is not symmetric — killing a process is instant, starting one is not, so the reply will not yet name a pid. Answers on a daemon with background listening switched off (`enabled: false`), because "nothing is listening" is the answer the caller came for |
| `wake.status` | — | `{mode, enabled, running, state, muted, capturing, pid, word, sensitivity, threshold, endpoint_silence_ms, ring_ms, detector, detector_pid, detector_rss_mb, activations, restarts, last_reason}` | Background listening as it actually is. `enabled` is the configured mode; `running` is whether the listener was started (a configured wake word whose detector is not installed is `enabled: true, running: false`, with `last_reason` saying why); `capturing` and `pid` are the live capture process, which is what makes "is my microphone open?" checkable against `ps` rather than merely believable. `activations` counts wake words since the daemon started — divide by uptime to measure your own false-activation rate. With the feature off, only `mode`, `enabled`, `running`, `state`, `muted`, `capturing`, `pid`, `word` and `last_reason` are present |
| `config.get` | — | `{path, fingerprint, fields, secrets}` | The editable settings with their **running** values: each field carries `key` (dotted TOML path), `label`, `type` (`string`/`int`/`float`/`bool`/`string_list`/`string_map`), `reload` class (`live`/`idle`/`restart` — see docs/configuration.md), `value`, and `enum` for closed sets. `fingerprint` identifies the file content on disk (`sha256:…`, or `missing`) for external-edit detection. `secrets` reports API-key **presence** only (`{endpoint, env, env_set, inline_key}`) — key values never travel over IPC in either direction |
| `config.set` | `{changes, fingerprint?}` | `{fingerprint, applied, reason?, needs_restart}` | Validates and writes field changes into config.toml (surgical rewrite preserving comments/unknown keys; atomic temp+rename, mode 0600), then applies them to the running daemon per reload class. `changes` maps dotted keys to values — native JSON types or strings (`"true"`, `"leftmeta,space"`, `"Golang=go lang,nginx=engine ex"` for a `string_map`), both accepted. Pass the `fingerprint` from your `config.get`: if the file changed on disk meanwhile the set fails with `-32002` instead of clobbering the hand edit. `applied: false` + `reason` means the file was written but a session was in flight — retry with `config.reload` once idle. `needs_restart` lists restart-class keys whose file value now differs from the running one |
| `config.reload` | — | `{fingerprint, needs_restart}` | Re-reads config.toml into the running daemon (the recovery path after a hand edit, and the retry after a busy `config.set`). A file that fails parsing or validation is refused with `-32001` and the running configuration is untouched; a session in flight refuses with `-32003` |
| `activity.get` | — | `{rows, limit}` | The activity feed (issue #70): recent daemon activity as rendered rows, oldest first — each `{seq, ts, session_id, kind, label, detail, failed}`, assembled daemon-side from bus events (the window is display-only, ADR 0013). `seq` increases monotonically for the daemon's lifetime and never repeats, so a client can merge this snapshot with `activity.row` pushes without duplicates; `limit` is the live `ui.activity_rows` bound. In-memory only — the ring dies with the daemon; conversations are the durable record. This is also the reconciliation path: pushes may be dropped for a slow client, the snapshot is what the daemon actually holds. Privacy contracts hold in every row: counts for memory and desktop context (ADR 0019/0025), lengths for typed text and search queries (ADR 0023/0028), per-tool argument summaries that default to nothing for unknown tools |
| `routines.list` | — | `{routines}` | The configured routines (ADR 0026), read-only: each entry is `{name, phrases, steps, incomplete, enabled}` where `steps` is a count, `incomplete` marks a captured routine (#62) still carrying a launch-command placeholder a human must resolve, and `enabled` is the shared switch (#93) — a parked routine still lists. The steps themselves are hand-edited TOML (`[[routines]]` in config.toml) and are not exposed or editable over IPC in v1 |
| `routines.run` | `{name}` | `{session_id}` | Runs one routine by name (case-insensitive) by starting a session and submitting the routine's first trigger phrase — exactly as if it had been spoken, so the intent router, the `routine.run` permission gate, the already-running refusal, and the spoken summary behave identically however a routine is triggered. An unknown name is `-32602` with a pointer to `routines.list`; a disabled routine (#93) is `-32602` saying "disabled" with the way back — its phrases are out of the grammar, so submitting one would reach the assistant, not the routine |
| `scripts.list` | — | `{scripts}` | The configured scripts (ADR 0030), read-only: each entry is `{name, phrases, path, report, timeout_sec, enabled}` with defaults applied; `enabled` is the shared switch (#93) — a parked script still lists. The path is deliberately listed — it is exactly what the `script.run` gate's confirmation names, and hiding it would make a substituted file harder to notice. Hand-edited TOML (`[[scripts]]` in config.toml); the definitions are never editable over IPC in v1 — which is itself a control: no IPC client can repoint a phrase at a different file — and `automations.set_enabled` can flip only the `enabled` key |
| `scripts.run` | `{name}` | `{session_id}` | Runs one script by name (case-insensitive) by starting a session and submitting the script's first trigger phrase — exactly as if it had been spoken, so the intent router, the `script.run` permission gate (ask by default: the confirmation names the script and its path), the one-at-a-time refusal, and the spoken outcome behave identically however a script is triggered. An unknown name is `-32602` with a pointer to `scripts.list`; a disabled script (#93) is `-32602` saying "disabled" with the way back |
| `automations.schedules` | — | `{schedules}` | Every scheduled routine and script (ADR 0032), read-only: each entry is `{kind, name, schedule, announce, next_fire, running, would_refuse, last_fired?, rule?}`. `next_fire` is computed daemon-side (RFC 3339, local offset), so no client re-derives schedule arithmetic; `would_refuse` carries the current tier verdict — true when the entry's identity is anything short of allow, with the deciding `rule` — so "needs `script.run` = allow" is visible before a 2am notification teaches it. A disabled entry (#93) is absent: parked means off the clock. The `schedule` keys are part of the hand-edited tables and are not editable over IPC |
| `automations.list` | — | `{fingerprint, automations}` | The Automations tab's one read (#93): routines and scripts as a single collection in declaration order (routines first). Each entry is `{kind, name, phrases, enabled}` plus its kind's facts — `{steps, incomplete}` for a routine; `{path, path_problem?}` for a script, where `path_problem` appears only when the file rotted under the running daemon (load validation refused a bad path; the recheck is the runner's own rule) — plus, when the entry carries a schedule, `{schedule, announce}` and, only while the scheduler holds it (enabled entries), `{next_fire, running, would_refuse, last_fired?, rule?}` exactly as `automations.schedules` serves them. `last_run` (`{at, outcome, failed, duration?, duration_ms?}`) appears only for a run this daemon has itself observed — the activity ring's honesty: absent means "has not run since boot", never fabricated; `outcome` and `duration` are worded daemon-side. `fingerprint` is the config file's, for `automations.set_enabled`'s external-edit check |
| `automations.set_enabled` | `{kind, name, enabled, fingerprint?}` | `{fingerprint, applied, reason?}` | Parks or resumes one routine or script (#93), persisted into config.toml through the same surgical entry editor as `knowledge.set_enabled` (one implementation, shared): only that entry's `enabled` key changes — comments, sibling entries, and `[[routines.steps]]` sub-tables byte-preserved — the result is validated whole before anything is written, the write is atomic, and the standard reload recompiles the intent grammar and rebuilds the schedules. Disabling takes the phrases out of the grammar and the schedule off the clock; re-enabling a phrase another entry took meanwhile is a `-32001` validation refusal carrying the same collision error a config load gives (both owners named), nothing written — never a half-enable. A stale `fingerprint` is a `-32002` conflict carrying the fresh one. Enabling is not an execution path — no gate beyond config-write authority; running stays on `routines.run` / `scripts.run`, which always face the gate |
| `config.get_entry` | `{family, name}` | `{fingerprint, family, entry}` | One whole `[[family]]` entry as the parser sees it (#99) — every key, sub-tables included — paired with the config file's fingerprint from the same read. This is what the window's form opens with and round-trips: it edits the fields it shows and carries every other key (`report`, a captured step's `size`) back on save untouched. `family` is the table-array name — `routines`, `scripts`, or `knowledge.feeds` (#100 added feeds as the registry row ADR 0033 planned; memory is deliberately NOT a family here — memory.toml is not config.toml, see `memory.add`/`memory.update`); `name` matches case-insensitively. Unknown family or name is `-32602` naming it |
| `config.validate_entry` | `{family, name?, entry}` | `{valid, problems, next_fire?}` | Dry-run validation of one draft entry (#99): the draft is upserted into an in-memory copy of config.toml (`name` addresses the entry being edited; empty/absent means a new one) and the WHOLE document is validated with the loader's own rules — the real intent router compiled for phrase grammar and collisions (the error names both owners), the real schedule parser, the real script path checks, the zero-argument script shape (the entry schema has no argv or environment key to accept, ADR 0030). `problems` is `[{field, message}]`, each message keyed to the form field it belongs to — `name`, `phrases[1]`, `path`, `schedule`, `timeout_sec`, `steps[2].app`, … — with `""` for whole-entry problems; the wording is the config load's, verbatim. `next_fire` (RFC 3339) appears whenever the draft's schedule parses — the scheduler's own arithmetic as a preview. Never writes, never executes |
| `config.upsert_entry` | `{family, name?, entry, fingerprint?}` | `{fingerprint, applied, created, reason?}` | Writes one whole entry (#99): create (empty `name`) appends the rendered table at the end of config.toml; edit replaces exactly the named entry's block in place (rename allowed) — comments, sibling entries, and unrelated `[[routines.steps]]` sub-tables byte-preserved by the same editor discipline as `automations.set_enabled`. The pipeline is validate-whole-then-write: the exact `config.validate_entry` check runs first, and a failure is a `-32001` refusal carrying the field-keyed `problems` with NOTHING written — never a half-write. A stale `fingerprint` (the file changed outside the window since the form opened) is a `-32002` conflict carrying the fresh one, nothing written. On success the write is atomic, the standard reload recompiles the grammar and rebuilds the schedules, `config.changed` fires, and the activity feed carries a row naming the entry. Saving is not an execution path: nothing runs |
| `config.delete_entry` | `{family, name, fingerprint?}` | `{fingerprint, applied, reason?}` | Removes one entry whole (#99): its block, its sub-tables, and the comment glued to its header (a comment separated by a blank line — a section header — stays), everything else byte-preserved. Same guards as `config.upsert_entry`: fingerprint conflict is `-32002`, a removal the whole-document validation refuses is `-32001` with the problems, and only a valid result is written (atomic) and applied by the standard reload — phrases leave the grammar, the schedule stops. The activity feed carries a row naming the deleted entry |
| `doctor.get` | — | `{checks}` | The settings-relevant readiness subset of `jarvix doctor` — offline and fast (no provider probe, no audio round trips). Each check: `status` (`ok`/`warn`/`fail`), `name`, `detail`, `fix`, and `related` — the config key the check informs, so a settings screen can show readiness inline |

Errors use JSON-RPC error objects. Application errors (wrong state, no active
session) use code `-32000`; standard codes cover parse/method/params issues.
The config surface adds three codes, each with structured `data`:

| Code | Meaning | `data` |
|---|---|---|
| `-32001` | config.set/reload rejected by validation; nothing written/applied | `{problems: [...]}` — `config.Validate` messages, each prefixed with the offending key |
| `-32002` | config.toml changed on disk since the client's `config.get`; nothing written | `{fingerprint}` — the file as it is now; re-read and reapply |
| `-32003` | config.reload could not apply because a session is active; running config unchanged | — |

→ {"jsonrpc":"2.0","id":2,"method":"session.submit","params":{"text":"hello"}}
← {"jsonrpc":"2.0","id":2,"result":{}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"thinking","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"assistant.started","params":{"session_id":"s7","provider":"ollama"}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"responding","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"assistant.delta","params":{"session_id":"s7","content":"Hi"}}
← {"jsonrpc":"2.0","method":"assistant.delta","params":{"session_id":"s7","content":" there."}}
← {"jsonrpc":"2.0","method":"assistant.finished","params":{"session_id":"s7","content":"Hi there."}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"speaking","session_id":"s7"}}

## Events

Every event's params include `session_id` where a session is involved.

| Event | Params | Meaning |
|---|---|---|
| `state.changed` | `{state, session_id}` | Authoritative state transition |
| `recording.started` / `recording.stopped` | `{session_id}` | Microphone capture bounds |
| `transcript.partial` | `{text}` | Interim hypothesis (reserved; whisper.cpp V1 emits none) |
| `transcript.final` | `{text}` | Completed transcript |
| `context.captured` | `{sources, duration_ms}` | Desktop context was gathered for this turn (ADR 0019), immediately before the provider request. `sources` is an array of `{source, chars, truncated, redacted}` — **sizes and flags only, never content**, because events fan out to every connected client. Published only on turns that reach the model: a matched deterministic intent gathers nothing. Fetch the captured text itself with `context.last` |
| `knowledge.injected` | `{feeds, trimmed, est_tokens}` | Cached feed values were offered to the model for this turn (ADR 0031), beside the desktop context. **Counts and estimates only, never values** — feed values may be sensitive; they are fetched with `knowledge.status`, over the socket, on request. Published only on turns that reach the model, and only when at least one opted-in feed had a value |
| `knowledge.updated` | `{feed}` | A fetch attempt for this feed completed — scheduled or `knowledge.refresh_now`, success or failure — so an open Knowledge tab re-requests `knowledge.status`. **Name only, never the value or the error**: those ride the status reply, over the socket, on request |
| `memory.injected` | `{facts, trimmed, searchable, total, est_tokens}` | Remembered facts were offered to the model for this turn (ADR 0025), immediately before the provider request; `searchable` counts the facts deliberately behind `memory.search` under ADR 0037's split. **Counts and estimates only, never content** — fact text is fetched with `memory.last`, over the socket, on request. Published only on turns that reach the model, and only with memory enabled |
| `memory.entry_changed` | `{action, id, chars}` | A fact was added, edited, pinned, or unpinned through the window (`memory.add` / `memory.update` / `memory.set_pinned`, #100/#104), so an open Memory tab re-requests `memory.list`. **Id and size only, never the words** — content travels over the socket, on request, like every other memory surface |
| `config.entry_changed` | `{action, family, kind, name, source}` | One `[[family]]` entry was created, edited, or deleted through the entry verbs — the window's forms (#99/#100) or the assistant's config tools (#105); `source` (`window` \| `assistant`) says which, and the activity row words it ("saved from the window" / "saved by the assistant"). Listings refresh off the accompanying `config.changed` |
| `config.setting_changed` | `{key, source}` | One registry setting changed through `config.set` — the settings screen or CLI (`source: user`) or the assistant's `config.write_setting` tool (`source: assistant`, #105). One event per changed key, in sorted order, after the accompanying `config.changed`. **Key and source only, never the value** — a value can be a whole system prompt; values travel over `config.get`, on request |
| `assistant.started` | `{provider}` | Provider request opened |
| `assistant.delta` | `{content}` | One streamed response fragment |
| `assistant.finished` | `{content, tool_calls}` | Full response text. `tool_calls` counts the tool calls the model requested this turn — attempts, including denied and declined ones. Zero on an answer that claims action is the model narrating work it never asked to do, which is exactly what the activity feed's text-only marker makes visible |
| `tool.started` / `tool.finished` | `{tool, arguments, detail?}` / `{tool, duration_ms, outcome}` | Bounds of one real tool execution — never published for denied or declined calls. `detail` is present only for tools that can run long (an advisor consultation) and is a short label to show for the duration, e.g. `Consulting claude…`. `outcome` is `ok`, or `error` for the registry's own failures (unknown tool, infrastructure err) — the one failure shape this layer can attest to; a tool that ran and refused reports its reason in its own audit events (`typing.audit`, `desktop.refusal`) |
| `tool.progress` | `{tool, message, elapsed_sec}` | A tool has been running for `elapsed_sec` seconds and is still going. Published **at most once** per call, and only for tools that carry a `detail` label; `message` is also spoken aloud. Reassurance, not a countdown — clients should show it and expect nothing further until `tool.finished` |
| `tool.confirmation_required` | `{tool, command, summary, rule, timeout_sec}` | The permission gate paused a tool call (state `awaiting_confirmation`). `command` is the exact command, verbatim; `summary` is the spoken question, generated daemon-side from the command; the overlay and the conversation window's confirmation card display `command` **verbatim** — clients must never summarise or re-derive it (ADR 0014). For `advisor.ask`, `command` is the advisor's name — what the user is actually approving, and what a remembered approval is keyed on |
| `tool.confirmation_deadline` | `{tool, command, deadline_ms, timeout_sec}` | The confirmation countdown started: the pending call auto-declines at `deadline_ms` (Unix milliseconds). A separate event because the clock starts only once the question has been *asked* — `tool.confirmation_required` goes out before the question is spoken, so it cannot honestly carry a deadline. Clients derive the countdown from `deadline_ms`, never from a hardcoded timeout; until this event arrives, `timeout_sec` from `confirmation_required` is the most that can be said. Not published when the confirmation resolved while the question was still being spoken |
| `tool.confirmed` | `{tool, command, source}` | The user approved; the call executes. `source`: `cli`, `text`, or `voice` |
| `tool.declined` | `{tool, command, source}` | The call will not run. `source`: `cli`, `text`, `voice`, `timeout`, `interrupted`, or `error` |
| `tool.denied` | `{tool, command, rule}` | A deny rule blocked the call outright; no confirmation is possible |
| `typing.audit` | `{tool, window, chars, approved, terminal, outcome, key?, reason?}` | Jarvix made a typing decision (ADR 0023). `outcome` is `typed`, `pressed`, `refused`, `focus-changed`, or `unavailable`; `approved` says whether a human confirmed this exact action rather than the configured tier allowing it; `terminal` marks a target whose contents are a command line. **The typed text is never published**: the payload may be a password the user dictated, and a bus event reaches every subscriber. `chars` is how many characters, never which. The daemon retains the most recent one for `jarvix status --last` |
| `desktop.action` | `{verb, target}` | Jarvix acted on the desktop (ADR 0022). `verb` is `focus`, `move`, `close`, `launch`, or `list`; `target` names the window as a person would (`firefox — GitHub`) or the application started. Published after the action succeeded, so it is a record of what happened, not what was attempted. Window addresses are never published: they are compositor internals and nothing spoken or shown needs them |
| `desktop.refusal` | `{verb, target, reason}` | Jarvix tried to act on the desktop and could not (issue #70): a launch the resolver refused (`launch` / `firefox` / `it is not installed`), a launch that failed to start, a dispatch the compositor rejected. `reason` is composed to be safe on the bus — the resolver's own spoken-form sentence, or a generic clause where the underlying error is operator material (launcher errors, compositor diagnostics, which stay in the journal). Window addresses never travel, same as `desktop.action` |
| `activity.row` | `{seq, ts, session_id, kind, label, detail, failed}` | One rendered activity-feed row, pushed as it is appended to the ring — the live half of `activity.get`, same shape, merged by `seq`. Derived by the daemon's own feed subscriber from the event that caused it, so it may trail that event on the wire (see ordering below). Clients render it verbatim; the wording is decided and tested daemon-side |
| `intent.executed` | `{intent, source, status, acknowledgement, duration_ms, slot?, routine?, script?, error?}` | The deterministic intent router handled the utterance locally, with no provider request (ADR 0017). `intent` is the id (`volume.set`, `speech.stop`, `custom.lock the screen`); `source` is `builtin`, `user`, `routine`, or `script` (with `routine`/`script` naming which — ADR 0026/0030; a layout capture, #62, reports `intent: routine.capture` with `routine` naming the saved entry); `status` is `ok` or `failed` (with `error` when the command failed, was declined, or was denied); `slot` is the validated integer for intents that take one; `duration_ms` is measured from the final transcript. `acknowledgement` is what Jarvix says — flash it in the overlay; it is empty for `speech.stop`, where silence is the confirmation |
| `routine.started` | `{routine, steps}` | A routine began executing (ADR 0026): its name and how many steps it will run |
| `routine.step` | `{routine, step, app, workspace, launched, status, detail?}` | One step finished: `step` counts from 1, `launched` distinguishes a fresh launch from a deduped existing window, `status` is `placed` or `failed` (with `detail` naming why). Progress for the bar and the window — the user only ever *hears* the final summary |
| `routine.finished` | `{routine, placed, failed, failures, summary, duration_ms}` | The routine completed: how many steps landed, the failure clauses, the summary sentence that was spoken, and how long the run took (#93 — the Automations tab's last-run line words the same number the log reports). Not published for a cancelled run — `session.cancelled` owns that ending |
| `script.started` | `{script, path}` | A configured script began executing (ADR 0030): its name and the exact file being run — the same path the gate's confirmation named, repeated on the audit surface. Never the script's output, in this event or any other |
| `script.finished` | `{script, path, status, exit_code, timed_out, duration_ms}` | The script ended: `status` is `ok` or `failed`, with the exit code and duration always present — success included, so "did my backup actually run?" is answerable from the feed. Not published for a cancelled run — `session.cancelled` owns that ending. Output (stdout/stderr) is deliberately absent: it can contain anything the script read, and events fan out to every connected client |
| `automation.fired` | `{kind, name, schedule, announce}` | A schedule fired (ADR 0032): the clock, not a person, started what follows. The run itself reports through the ordinary events above — the session it starts is a normal session, quiet unless `announce` is true |
| `automation.skipped` | `{kind, name, schedule, reason}` | A scheduled firing did not run, with the reason: the previous run was still going (a schedule is not a queue), or a conversation was active (the clock never interrupts a person). Reported so a skipped firing is a row, never a silence |
| `automation.refused` | `{kind, name, schedule, reason, rule}` | A scheduled firing of an entry whose tier is anything short of allow: nothing executed — a schedule cannot answer a confirmation question — and the deciding policy `rule` is on the record. Accompanied by a desktop notification whose click opens the window |
| `automation.missed` | `{kind, name, schedule, due}` | Boot found a firing that fell while no daemon was running: reported once, with when it was due (RFC 3339) — and never re-fired, because the daemon cannot know whether 3am's intent still holds at 9am. Say the phrase to run it now |
| `wake.detected` | `{confidence}` | The wake word was recognised and a session is starting (ADR 0024). Published **before** transcription, so the overlay can acknowledge the wake word while whisper is still working. It carries a confidence and nothing else — never audio, never text: events fan out to every connected client, and pre-wake audio does not leave the daemon |
| `wake.changed` | `{state}` | What the microphone indicator should show: `off` (nothing is capturing), `armed` (a capture process is running), or `muted` (`jarvix mute` is in force). A second dimension alongside `state.changed` rather than another session state — a session state describes a turn, this describes the microphone between turns |
| `tts.started` / `tts.finished` | `{}`; finished may carry `{interrupted:true}` | Speech bounds |
| `session.timings` | `{capture_to_transcript_ms?, context_ms?, transcript_to_first_delta_ms?, first_delta_to_first_pcm_ms?, first_pcm_to_audio_out_ms?, tool_ms?, confirm_wait_ms?, release_to_first_audio_ms?, jarvix_ms?}` | The session's latency budget, published immediately before `session.finished` (ADR 0018). Each key is a completed stage in milliseconds; **a stage that did not happen is absent, not zero** — a typed question has no capture stage, a silent answer has no audio stages, and a turn with desktop context disabled has no `context_ms`. `context_ms` is desktop-context gathering (ADR 0019), which sits between the transcript and the request: the model's clock starts where it stops, so gathering is counted in `jarvix_ms` rather than excused as thinking time. `transcript_to_first_delta_ms` is the model's time to its first output — a text token or a tool call — which is the user's choice of model, not Jarvix's latency. `tool_ms` (time inside tool executions) and `confirm_wait_ms` (time waiting on the user's confirmation answer) are the turn's **excluded spans** (issue #72): reported so the turn's real length is on the record, attributed to neither Jarvix nor the model, and subtracted from any pipeline stage they fell inside. `jarvix_ms` is `release_to_first_audio_ms` minus thinking minus the excluded time before the first sound — the number Jarvix is accountable for, **non-negative by construction** (every stage is; a span whose accounting cannot be reconciled is dropped rather than published negative). Also emitted as one structured log line with identical keys |
| `session.finished` | `{}` | Session completed (also after an error) |
| `session.cancelled` | `{reason}` | Session cancelled or interrupted. The exchange the session was carrying — the user's turn and any partial answer — is committed to working memory and the archive **marked interrupted** before this event is published (issue #117), so a `conversation.*` read issued after seeing it already finds the exchange (the same read-your-acknowledged-writes barrier `session.finished` gets). A session cancelled before it had a transcript commits nothing — there is no exchange to keep |
| `error` | `{stage, message}` | A stage failed: `audio`, `stt`, `assistant`, `tts`, `session` |
| `config.changed` | `{fingerprint}` | Configuration was saved (`config.set`) or reloaded; open settings views should refresh via `config.get` |
| `conversation.changed` | `{reason, conversation_id?}` | The live thread changed underneath open views: `reset` (`jarvix new`, a delete of the active conversation) or `opened` (an archived conversation was reopened, ADR 0027). Re-request `conversation.get` rather than guessing what the change meant |

States seen in `state.changed`: `idle`, `listening`, `transcribing`,
`thinking`, `responding`, `awaiting_confirmation`, `acting`, `speaking`,
`cancelling`, `error`. `acting` is a matched deterministic intent — it never
passes through `thinking`/`responding`, because no provider request is open.

Ordering guarantees: `state.changed` precedes the stage events it enables;
`session.timings` immediately precedes `session.finished`; and
`session.finished`/`session.cancelled` is always the last *engine* event of a
session. `activity.row` is exempt from that last clause: it is derived — the
daemon's feed subscriber rendering engine events it has just received — so a
row for a session's final events can arrive shortly after `session.finished`.
Rows do preserve their own order (`seq`), and a client that treats
`session.finished` as terminal loses nothing: `activity.get` reconciles.
Slow consumers may lose events (the daemon never blocks on a client), so the
overlay treats `state.changed` as the source of truth and resyncs with
`status.get` on reconnect.

## The shell plugin's own IPC surface

Separate from the daemon socket above: the Omarchy shell exposes each
plugin's `IpcHandler` through `omarchy-shell <target> <function>`. Jarvix
registers two targets, and this is how the CLI, notifications, and the bar
widget reach the plugin's windows without the daemon being involved — which
matters, because the window and the widget must work with jarvixd stopped.

| Target | Function | Effect |
|---|---|---|
| `jarvix` | `openWindow` / `closeWindow` / `toggleWindow` | Show, hide, or toggle the conversation window. `jarvix window`, a clicked notification, and the bar widget all go through here — there is only ever one window. A compositor-killed window (super+W) is rebuilt on the next open rather than re-shown; `scripts/verify-window-kill.sh` checks that live (issue #106) |
| `jarvix` | `openSettings` | Open the window already showing the Settings tab (the bar widget's Settings action) |
| `jarvix` | `state` / `ping` | The overlay's view of the session state; liveness |
| `jarvix.bar` | `open` / `close` / `toggle` / `show` / `hide` | The bar widget's panel |
| `jarvix.bar` | `state` | The state key the bar icon is showing — one of the daemon states above, or `not-running`, `error`, or `working` (an unrecognised state), or `wake-armed` / `wake-muted` when the daemon is idle and background listening is on. `scripts/verify-bar-widget.sh` reads this to check the icon against the daemon |

The widget's own vocabulary — the glyph, words, and urgency for each state —
is defined in `internal/desktop/barstatus.go` and generated into
`plugin/omarchy/BarState.js`; see [ADR 0020](adr/0020-bar-widget-not-tray-icon.md).
The same arrangement covers the activity feed: row wording lives in
`internal/desktop/activity.go` (rows arrive from the daemon already
rendered), and the window's glyph-per-kind table is generated into
`plugin/omarchy/ActivityState.js`.
