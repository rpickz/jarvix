# Jarvix IPC protocol

## Transport

- **Socket:** `$XDG_RUNTIME_DIR/jarvix.sock`, mode `0600`. No TCP listener
  exists.
- **Framing:** newline-delimited JSON (one JSON document per line).
- **Protocol:** JSON-RPC 2.0. Clients send requests; the daemon sends
  responses, plus **notifications** (no `id`) for asynchronous events, pushed
  to every connected client.

A stale socket left by a crashed daemon is detected (connect fails) and
replaced on startup; a live socket makes a second daemon refuse to start.

## Versioning

`status.get` returns `protocol` (currently `1`). Incompatible protocol
changes bump it; clients should check it once after connecting. Additive
changes (new methods, new events, new fields) do not bump the version —
clients must ignore unknown events and fields.

## Requests

| Method | Params | Result | Notes |
|---|---|---|---|
| `session.start` | — | `{session_id}` | Cancels any active session first (interruption) |
| `voice.start` | — | `{}` | Idle → Listening; starts capture |
| `voice.stop` | — | `{discarded}` | Listening → Transcribing; transcription runs async. `discarded: true` means the capture was shorter than `audio.min_recording_ms` and the session ended quietly (`session.cancelled`) — skip the follow-up `session.submit` |
| `session.submit` | `{text?}` | `{}` | With `text`: skip audio, go think. Without: proceed when the transcript lands |
| `session.text` | `{text}` | `{session_id, confirmation, approved?}` | One typed turn, for a client with a text field (the conversation window's composer). Composes `session.start` + `session.submit {text}` — the `jarvix ask` path — but decides between them and a pending confirmation **in the daemon**, under one lock: with `awaiting_confirmation` in force the text answers the confirmation (`confirmation: true`, `approved` being the same reading a spoken yes/no gets) and the waiting session is left alone; otherwise a new session starts, cancelling any session in flight. Text that is empty or whitespace is rejected with `-32602` and starts nothing. Do not sequence `session.start` yourself from a text field: the state you read can go stale in the round trip, and starting a session then abandons the confirmation the user was answering |
| `session.cancel` | — | `{}` | Stops everything; no-op when idle |
| `session.confirm` | `{approved?, remember?}` | `{approved, remembered?, remember_scope?}` | Answers a pending tool confirmation (`approved` defaults to `true`); errors when nothing is pending or a voice reply is already being captured. The one resolution verb every button is a thin client of: the window card's ✓/✗ and the overlay's ✓/✗ (issue #119) both send exactly this call, and both surfaces resolve on the daemon's `tool.confirmed` / `tool.declined` event rather than on their own click — there is no second resolution path. `remember` is the standing-grant scope (#162, ADR 0053): `"always"` appends the rule to `[tools.policy] shell_allow` and recompiles the running gate before resolving, `"conversation"` grants it in memory only, and omitting it is the ordinary approve-once. **It is a scope word and never a pattern** — the rule written is the one the daemon derived and published on `tool.confirmation_required`, so no client can name what it is granting. A scope the daemon does not know is `-32602`, as is remembering a shape the gate refused (`remember_reason` says why) or asking to remember a decline; in each case the confirmation is left standing rather than half-answered, so the user can still answer it another way. The reply names the rule that was added |
| `speech.cancel` | — | `{stopped}` | Stops spoken output whenever audio is actually playing, whatever the session state — mid-answer tool rounds included (issue #54). Stopping speech ends the turn (`tts.finished {interrupted: true}` when the answer had started speaking, then `session.finished`); a pending tool confirmation is abandoned as declined. `stopped: false` reports that nothing was playing — a no-op, not an error |
| `speech.replay` | `{turn?, role?}` | `{turn, role}` | Speaks one turn of the **live** conversation again (issue #122) — the window's per-message control and `jarvix say-again` are thin clients. `turn` is the turn's 1-based position in the `conversation.get` snapshot (the window's own transcript numbering; positions only append while a thread lives, and a rebuilt or reopened window re-reads the same snapshot, so the address survives both); absent or `0` means the newest assistant turn. The daemon resolves the text **from its own record** — a client sends an address, never text for the voice to read — and speaks it through the standard pipeline (same speaker, normalization, lexicon, voice), as its own speech turn: `acting` → `speaking` → `idle`, `tts.started`/`tts.finished`, a `speech.replayed` event and an activity row — but **no conversation write**: a replay is not a new turn. Every snapshot turn is replayable as shown — an interrupted turn reads its bracketed annotation, a confirmation record reads its spoken summary, never the verbatim command. `role`, when sent, must match the addressed turn's role: it guards a stale view (the live window model can trail the record) and a mismatch is `-32602` — refresh the snapshot and retry — as are out-of-range addresses and speech being disabled. Precedence is pinned: **live conversation speech wins** — any active session refuses with `-32000` (a visible "busy" cue, never a replay talking over the conversation) — while new live speech supersedes a replay in progress instantly (the standard interruption), and a second replay supersedes the first the same way. The stop word and `speech.cancel`/`session.cancel` stop a replay like any speech |
| `conversation.reset` | — | `{}` | Forget carried-over context (and any remembered tool approvals); the next turn starts a fresh thread. With retention on (ADR 0027) the old thread is already archived — turns are appended as they complete — so the reset only detaches it; it stays listed and reopenable. A session in flight is deliberately left alone — use `conversation.new` for the user-facing "new chat". Publishes `conversation.changed {reason: "reset"}` |
| `conversation.new` | — | `{}` | The explicit end of a conversation (issue #117, ADR 0038) — the one verb every New Chat surface is a thin client of: `jarvix new`, the window's New chat button, the bar menu item (the spoken "start a new conversation" intent reaches the same engine path from inside its own session). `conversation.reset` plus: a session in flight is cancelled first, and its exchange is committed **marked interrupted** into the thread being ended — archived and searchable, never dropped. The next utterance starts a fresh thread. Publishes `session.cancelled` (when a session was running) then `conversation.changed {reason: "reset"}` |
| `conversation.get` | — | `{turns, state, session_id, state_since_ms, error_stage, error_message, tool?, tool_detail?, confirmation?}` | Snapshot of the current conversation for display: `turns` is an array of `{role, text}` (`user`/`assistant`, oldest first, including the in-flight user question once transcribed). A **resolved** tool confirmation is a turn of its own (issue #118): `{role: "confirmation", text, confirmation: {tool, command, rule?, outcome, source?, timeout_sec?, remembered?, remember_scope?}}` — `text` is the spoken question, `command` is verbatim (ADR 0014), `outcome` is `approved`, `declined`, or `timed_out` (never conflated), and it sits at the position the exchange happened, so a reopened window renders it as the static resolved card. Render it on open, then live-append from `assistant.delta` / `transcript.final` / `state.changed` / `error` events. `confirmation` is present only while a tool confirmation is pending: `{tool, command, summary, rule, timeout_sec, deadline_ms?, remember_pattern?, remember_segment?, remember_reason?}` — the same facts `tool.confirmation_required` / `tool.confirmation_deadline` carried, so a window opened *during* the wait can render the confirmation card (question, verbatim command, countdown) without having seen those events (issue #76). `deadline_ms` is absent while the question is still being spoken. `error_stage` / `error_message` carry the last failure, held until the next session starts, so a window opened by clicking the error notification can still render it. `state_since_ms` is when the current state began (the same clock `state.changed`'s `since_ms` uses), and `tool` / `tool_detail` name the tool call executing right now — present only while one is — with `tool_detail` its own progress label (`"Consulting claude…"`). Together they are everything the conversation window's pending assistant turn is built from (issue #158), so a window opened mid-thought shows the same thing, counting from the same instant, as one that was already open. An assistant turn that consumed something retrievable also carries `provenance: {sources: [{kind, strength, ref?, tool?, subject?}], truncated?}` (issue #168) — what went into that answer, as references only; the key is absent on every turn that used nothing. Resolve it with `provenance.resolve`; never render it raw |
| `conversation.list` | — | `{retention, active_id, conversations, unreadable}` | The archive (ADR 0027), newest first: each `{id, started, last_active, turns, preview}`. Metadata only — no transcript is opened, so a large library lists fast. `unreadable` (`{id, error}` each) names conversations that could not be parsed: one bad file never hides the library, or itself. `retention: false` means `conversation.retention = "off"` — nothing new is being archived, but the listing (and deletion) still work. `active_id` is the conversation the live thread belongs to, `""` when none. Read-your-acknowledged-writes: a turn whose `session.finished` has been published is already in the listing — and reflected in `active_id` — by the time any `conversation.*` read issued afterwards answers; the daemon flushes the archive before reading, never the other way round (issue #115) |
| `conversation.read` | `{id}` | `{id, started, last_active, preview, turns}` | One whole archived conversation, read-only: `turns` is an array of `{role, text, ts}` (RFC 3339), oldest first. A turn from an exchange the user cut off also carries `interrupted: true` (issue #117); its text ends in the bracketed annotation the record was committed with, so clients need no special rendering. A confirmation record turn (issue #118) carries `confirmation: {tool, command, rule?, outcome, source?, timeout_sec?}` with `role: "confirmation"` — the same structured record `conversation.get` serves, at its archived position between the turns of its exchange. An assistant turn carries `provenance` on exactly the terms `conversation.get` describes (issue #168), absent when the turn consumed nothing. Unknown or unreadable ids are `-32602` |
| `conversation.search` | `{query, limit?}` | `{retention, active_id, results, searched, skipped}` | Full-text search over the archive, live head included (ADR 0028) — including a turn that finished the instant before the query: `session.finished` published means the exchange is findable, and `current` on its hits truthful (issue #115). `results` is ranked best first — exact phrase beats scattered words, recency breaks ties — each `{id, turn, role, ts, passage, current}`: `turn` is the 1-based position in that transcript, `passage` the matched text clipped to one line, `current` true when the hit is in the active conversation ("earlier in this conversation"). `limit` caps results (default 10, ceiling 20). `searched` counts conversations scanned; `skipped` (`{id, error}` each) names ones that could not be — the listing's unreadable contract. A blank query is `-32602`. The window's search box and `jarvix conversations search` are thin clients; the model's `conversations.search` tool shares the same searcher. Queries and passages are never logged |
| `conversation.open` | `{id}` | `{id, turns}` | Reopens an archived conversation as the active thread — the explicit action. The engine keeps the most recent `history_turns` exchanges as model context (the archive keeps everything the prompt cannot), restarts the follow-up window, and appends follow-up turns to the same record. What went into each restored answer comes back with it (issue #168), within the same context-budget cut. Publishes `conversation.changed {reason: "opened", conversation_id}` |
| `conversation.delete` | `{id}` or `{all: true}` | `{deleted}` | Removes conversations from disk — files gone, no tombstones. Deleting the active conversation (or `all`) also resets the live thread, so the next turn cannot rebuild the record from working memory. Unknown ids are `-32602` |
| `provenance.resolve` | `{sources}` | `{items}` | Turns a turn's stored `provenance.sources` into the list a person reads (issue #168). Send back exactly the references the turn carried; each item comes back as `{kind, ref, strength, strength_phrase, name, gone?, note?, actions?}`. `name` is composed **now**, against the live stores — a remembered fact's content, a feed's name, an artifact's file — which is why nothing but references is ever stored. `strength_phrase` is the wording: `"available to the answer"` for something injected (in front of the model; not evidence it was used) and `"returned during this turn"` for a tool that ran and produced output. The two are never merged; clients render the phrase and word neither themselves. `gone: true` marks a source that no longer exists — forgotten fact, deleted feed, closed window, removed file — with `note` saying so plainly and **no** `actions` at all: never a dead button. An action is either `{id, label, tab, ref}`, which the client performs itself (open that tab at that item), or `{id, label, invoke: true}`, which it sends to `provenance.open`. Unknown kinds resolve to an honest, actionless row rather than an error |
| `provenance.open` | `{kind, ref, action}` | `{done}` | Performs the actions a client cannot: opening an artifact in the configured viewer (`artifacts.open_command`), opening a feed's page, focusing the window a focus thread is anchored to (issue #168). Every call re-checks what it is about to act on — the file may have been deleted, the window closed, the feed edited since the panel was drawn — and refuses with `-32602` rather than silently doing nothing. A feed's page goes **through the permission gate, never around it**: the gate is asked about `xdg-open <url>` under the shell tool's identity, and only a standing allow proceeds; an ask verdict means the user has not given leave, and a button press is not a moment at which Jarvix may ask for it (ADR 0053). An action a source does not have is `-32602` |
| `context.last` | — | `{captured, session_id?, at?, age_sec?, duration_ms?, sources?}` | The desktop context gathered for the most recent question that reached the model (ADR 0019) — the audit surface behind `jarvix status --last`. `captured: false` means nothing has been gathered yet this daemon lifetime. Each source is `{source, text, chars, truncated, redacted}`: `text` is **exactly what the model was sent**, already capped at `context.max_chars` and already replaced by `[looks like a secret — not shared]` if it matched the secret heuristics; `chars` is the pre-truncation length. Retained in memory only — never persisted, never surviving a restart |
| `memory.last` | — | `{enabled, injected, session_id?, facts?, trimmed?, searchable?, total?, est_tokens?}` | The remembered facts injected into the most recent question that reached the model (ADR 0025) — the memory half of `jarvix status --last`, beside `context.last`. `enabled: false` means `memory.enabled = false`; `injected: false` means no turn has consulted the knowledge base yet this daemon lifetime. `facts` is what the model was actually given — each in the `memory.list` fact shape — `trimmed` how many *ambient* facts the token cap left out of the block (never out of storage), `searchable` how many facts were deliberately not offered to the block at all (the unpinned rest under ADR 0037's split — reachable through the `memory.search` tool, not a loss), `total` the store size at injection time, `est_tokens` the block's estimated cost. Retained in memory only |
| `memory.list` | `{query?}` | `{enabled, path?, count?, max?, warning?, facts?}` | The store itself, straight from disk (hand-edits included): every remembered fact, or those matching `query` (case-insensitive substring or shared significant word), most recently confirmed first. Each fact is `{id, content, stored, updated, pinned, source?, times_retrieved?, last_retrieved?, last_retrieved_spoken?, previous?}`: `pinned` is the ambient flag (#104); the retrieval stats appear **only for facts `memory.search` has actually returned** — a never-retrieved fact carries no stats keys, so no client can render a fabricated zero — and `last_retrieved_spoken` is the feeds' shared spoken wording ("four minutes ago"), one scale for every surface. The supersede trail (`previous`: `{content, stored, superseded}` each) answers "when did that change". `warning`, when present, is the book's over-budget sentence (a pinned set past `memory.max_injected_tokens`, or an unpinned book that outgrew it): the Memory tab and `jarvix memory list` show it verbatim — a trim is never silent (ADR 0037). `path` names the file — it is the user's to edit; `count`/`max` report the store cap. `jarvix memory list` is a thin client |
| `vocabulary.list` | `{query?}` | `{enabled, path?, count?, max?, bias_count?, bias_max?, warning?, entries?}` | The taught vocabulary (issue #129, ADR 0042), straight from disk (hand-edits included): every taught entry, or those matching `query` (case-insensitive substring over phrase, meaning, and note), most recently taught first. Each entry is `{id, phrase, meaning, taught, updated, hard_to_hear, note?, source?, previous?}`; the supersede trail (`previous`: `{phrase, meaning, note?, taught, superseded}` each) answers "what did quid used to mean". `bias_count`/`bias_max` report the finite hard-to-hear budget (the STT bias list). `warning`, when present, is the store's over-budget sentence — taught words no longer fit `vocabulary.max_injected_tokens` — shown verbatim in the window's Vocabulary section: a trim is never silent (ADR 0037). `path` names the file — it is the user's to edit |
| `vocabulary.last` | — | `{enabled, injected, session_id?, entries?, trimmed?, total?, est_tokens?}` | The taught words injected into the most recent question that reached the model — the vocabulary half of the audit beside `memory.last`. `injected: false` means no turn has consulted the vocabulary yet this daemon lifetime. `entries` is what the model was actually given, in the `vocabulary.list` entry shape; `trimmed` how many the token cap left out of the block (never out of storage). Retained in memory only |
| `vocabulary.teach` | `{phrase, meaning, note?, hard_to_hear?}` | `{entry, warning?}` | The Vocabulary section's Add — and the one write path a re-teach lands on: an already-taught phrase (case/punctuation folded) is superseded in place, old meaning onto its trail, **never a silent second entry**. **Ungated**, on `memory.add`'s argument: typing a phrase into the form is the user's explicit teaching, and a wrong teach is undone with one forget. Empty phrase/meaning are `-32001` refusals with field-keyed `problems` (the entry-form wire shape); a store at `vocabulary.max_entries` is a `-32001` whole-entry problem; nothing written on any refusal. `hard_to_hear: true` also flags the phrase for the STT bias — refused at the bias cap with a `-32001` whose message says the entry itself WAS saved. `warning` carries near-cap sentences (store or bias list). Publishes `vocabulary.entry_changed` |
| `vocabulary.update` | `{id, phrase, meaning, note?, hard_to_hear?}` | `{entry, warning?}` | The section's Edit, by id: content changes supersede onto the trail, an untouched entry writes nothing, and a phrase rename onto another taught phrase is a `-32001` collision refusal naming the owner — two entries for one phrase is the state teach exists to prevent, whatever the surface. Unknown ids are `-32602`. Publishes `vocabulary.entry_changed` |
| `vocabulary.forget_gated` | `{id}` | `{session_id}` | The section's per-entry Delete: starts a session that runs the `vocabulary.forget` tool identity through the permission gate — the standard confirmation card appears naming the exact phrase and meaning, resolved from the store, and only an approval deletes. Gated because deletion destroys the entry's taught history (the ADR 0025 reversibility split, applied to vocabulary in ADR 0042). An unknown id is `-32602` and no session starts |
| `knowledge.status` | — | `{enabled, path?, fingerprint?, feeds?}` | The feed cache (ADR 0031): one entry per configured `[[knowledge.feeds]]` table — `{name, mode, enabled, interval_sec, ttl_sec, inject, has_value, stale, failing, value?, fetched?, age_sec?, age_spoken?, failing_since?, attempts?, last_error?}` — in declaration order. `age_spoken` is the shared spoken-style wording ("four minutes ago") so no client invents its own scale; `fingerprint` is the config file's, for `knowledge.set_enabled`'s external-edit check. `value` travels here deliberately (the user's own data over their own 0600 socket, the `memory.list` precedent) and nowhere else: logs and events carry names and counts only. `jarvix doctor` composes its "N fresh, M failing since …" line from this. Feed definitions remain plain `[[knowledge.feeds]]` TOML, and since #100 the window creates, edits, and deletes them through the generic entry-form verbs (`config.get_entry` … `config.delete_entry` with `family: "knowledge.feeds"`) beside the `enabled` switch and the manual refresh |
| `knowledge.refresh_now` | `{name}` | `{started}` | Fetches one feed immediately, through the exact scheduled-fetch path: same runner, same single-flight latch per feed (a refresh during an in-flight fetch is that fetch, not a second command), same gate identity — `knowledge.refresh` must resolve to allow, exactly as the scheduler requires. Asynchronous: the reply acknowledges the start, and completion arrives as `knowledge.updated`. Unknown, disabled, or gate-refused feeds are `-32602` with the reason |
| `knowledge.set_enabled` | `{name, enabled, fingerprint?}` | `{fingerprint, applied, reason?}` | Parks or resumes one feed, persisted into config.toml through the surgical entry editor: only that entry's `enabled` key changes — comments and sibling entries byte-preserved — the result is validated whole before anything is written, the write is atomic, and the running scheduler drops/readopts the feed on the same reload path hand edits use. A `fingerprint` (from `knowledge.status` or `config.get`) that no longer matches the file is a `-32002` conflict carrying the fresh fingerprint — hand edits are never clobbered. `applied: false` with `reason` means written but pending (a session was busy), the `config.set` contract. A disabled feed keeps its last cached value, is listed with `enabled: false`, and nothing fetches or injects it |
| `memory.forget` | `{id?}` or `{query?}` | `{forgotten, fact?, matches?}` | Deletes one fact from disk — trail and all; deletion is deletion. By `id`, or by `query` when it matches exactly one fact; several matches delete **nothing** and come back as `matches` for the caller to pick an id from (the same refuse-to-guess rule the model-facing tool follows). An unknown id is `-32602`; so is calling it with memory disabled |
| `approvals.list` | — | `{path, approved, denied}` | What runs without asking, and what is refused outright (#162, ADR 0053; #164, ADR 0054). `approved` is one row per standing grant, permanent ones first in configuration order and conversation-scoped ones after: `{pattern, source, scope, uses, added?, last_used?}` — `source` is `card` (agreed to on a confirmation card) or `hand` (found in `config.toml` with no ledger record), `scope` is `always` or `conversation`, and `added`/`last_used` are RFC 3339 and **absent** rather than zero when there is no such date, so no client renders an invented one. `path` names the file the permanent rules live in — it is the user's to edit. Membership always comes from the running gate's `shell_allow`, so a hand edit wins. `denied` is one `{pattern}` row per configured `shell_deny` rule, from the running gate too — a person asking what runs unasked is owed the other half, because a deny rule is the reason something they granted still asks. It carries no ledger: the ledger counts standing GRANTS being used, and a deny rule's whole job is that nothing happens. `jarvix approvals list` and the window's Approvals tab are thin clients |
| `approvals.forget` | `{pattern, list?, confirmed?}` | `{forgotten, pattern, list, scope?, approved?, denied?, confirm_required?, confirmation?}` | Removes one rule from one list, matched after whitespace collapsing. `list` is `allow` (the default, and what `jarvix approvals forget` sends) or `deny`. **Forgetting an allow rule is deliberately easy**: no fingerprint, no confirmation, and an unknown pattern is `{forgotten: false}` with the current list rather than an error — tightening the gate is never the direction to make hard. It revokes conversation-scoped grants too, and a permanent revocation rewrites `[tools.policy] shell_allow` and recompiles the running gate immediately; no restart. **Removing a deny rule asks first** (#164, ADR 0054): the call without `confirmed: true` removes nothing and answers `{confirm_required: true, confirmation}`, where `confirmation` is the daemon's sentence naming what the rule protected — the commands it refuses, that the refusal beat every allow rule, and what those commands will do instead. Repeat with `confirmed: true` to remove it. The two-step is on the wire, not in a client, so nothing can skip it by not implementing it |
| `approvals.add` | `{pattern, list, fingerprint?}` | `{added, pattern, list, reason?, shadows?}` | Adds one rule a **person** typed to one list (#164, ADR 0054) — the Approvals view's add form. `list` is **required**: a default would mean a request that forgot the field widened the gate. An `allow` pattern faces the confirmation card's own refusal matrix, imported rather than restated (`Policy.VetAllowPattern`), so the two routes to `shell_allow` cannot disagree — a refusal is `-32001` with the matrix's own sentence, field-keyed as `problems: [{field: "pattern", message}]`, and nothing is written. Two rules differ from the card's derived pattern because a person typed this one: every word must be a command word (a flag is refused rather than silently dropped, since a rule that stopped before it would be *wider* than the one typed), and there is no three-word cap (a longer prefix is strictly narrower, so strictly safer). A `deny` pattern faces no matrix at all — a gate that argued with someone making it stricter is a gate people route around — but the receipt carries `shadows`, the allow rules it now beats. A pattern already on the list is `{added: false}` with a `reason` for deny, and for allow is refused by the matrix's own "already covered" clause. The write is the same surgical, fingerprint-guarded, compile-before-write, atomic path a remembered rule takes, and publishes `approvals.changed`. **This is the only IPC method that accepts a pattern on the granting path, and `session.confirm` still does not**: the card exists in response to something the model asked for and must derive its rule, while nothing here happens in response to the model |
| `memory.forget_gated` | `{id}` | `{session_id}` | The window's per-fact Forget (#92): starts a session that runs the `memory.forget` tool identity through the permission gate, so the standard confirmation card appears naming the exact fact — resolved from the store, never from the caller — and only an approval deletes, through the registry with the ordinary `tool.*` audit events. Where `memory.forget` above is the CLI's deliberate direct line, this is the path for a button in a listing. An unknown id is `-32602` and no session starts |
| `memory.add` | `{content, pinned?}` | `{fact, warning?}` | The Memory tab's Add (#100): stores one new fact through the memory book's own write path — the same discipline `memory.remember` writes with (id assigned from the never-reused high-water mark, timestamps set, atomic fsync-and-rename). **Ungated**, per ADR 0025's reversibility split: typing a fact into the form is the user's explicit word, exactly like a spoken "remember that …", and a wrong add is undone with one forget. `pinned: true` (#104) creates the fact ambient in one save. Empty content is a `-32001` refusal with `problems: [{field: "content", message}]` — the entry-form wire shape, so the window's dialog code is shared — and a store at `memory.max_facts` is a `-32001` whole-entry problem; both write nothing. `warning` carries the book's near-cap sentence when the store is filling. Publishes `memory.entry_changed` |
| `memory.update` | `{id, content, pinned?}` | `{fact}` | The Memory tab's Edit (#100): supersedes one fact's text through the book — the old value moves onto the fact's `previous` trail with both timestamps, so nothing is destroyed and "when did that change" stays answerable, which is what makes this verb safe ungated (Forget, the destructive one, keeps its confirmation card). Since #104 the form sends `pinned` alongside the content and the daemon compares before writing: unchanged text with a toggled pin changes only the pin — no revision of identical wording is ever manufactured — and unchanged everything writes nothing. Refusals share `memory.add`'s shapes: empty content is field-keyed `-32001`, an unknown id is `-32602` naming it, and nothing is written on any refusal. Publishes `memory.entry_changed` |

the wording is the config load's, verbatim. `next_fire` (RFC 3339) appears whenever the draft's schedule parses — the scheduler's own arithmetic as a preview. `secrets` is the write-only credential channel (#163): `{api_key: {action: "keep"|"set"|"clear", value?}}`, an instruction about the stored value rather than a copy of it — absent means keep, so a client that has never heard of credentials cannot delete one by omission, and an entry that carries the credential key itself is refused by shape. `notes` mirrors `config.get_entry`'s. `preview` appears for the families that declare one — today only `routines` (#181, ADR 0059) — and is the routine editor's diagram, computed from the document the save WOULD write so the picture is drawn from the values a load would read: `{steps, workspaces}`, where each step is `{index, workspace, launches, summary}` (the summary is the arrangement in one sentence, the accessibility channel the drawing cannot be) and each workspace is `{workspace, heading, monitor?, drawable, unavailable?, aspect?, usable, panels, problems?, summaries}`. `aspect` is the target screen's logical width over its height and `usable`/`panels` are rectangles as fractions of that screen's glass — `{x, y, width, height}` — so a client multiplies a fraction by the width of a box and computes no placement of its own (ADR 0013). A panel also carries `{step, label, kind, share, size, note?}`, all worded daemon-side. `drawable: false` is a first-class answer with `unavailable` saying why — a screen that is not plugged in, a share the vocabulary refused, two windows asking for more of an axis than it has — and `problems` then carries the field-keyed refusals, so the preview never shows a layout that will not happen. Never writes, never executes |
| `reminders.preview` | `{when}` | `{valid, due?, due_spoken?, problems?}` | The create form's dry run (#164, ADR 0054): resolves one time expression against the daemon's clock and says which moment it means, storing nothing. Same parser as speech (`intent.ParseWhen`), same next-occurrence rule, same wording — `due_spoken` is the sentence a spoken reminder hears back ("at nine tomorrow morning"), so no client does clock arithmetic (ADR 0013). An unreadable expression is **not an error**: it comes back `{valid: false, problems: [{field: "when", message}]}`, because the form asks about text somebody is still typing and every keystroke of a half-written "at thre" would otherwise be a transport failure |
| `reminders.create` | `{when, text}` | `{spoken}` | Sets one reminder from typed words (#164, ADR 0054). It calls the spoken path's own verb: same time grammar, same store, same next-occurrence rule, same confirmation sentence — `spoken` is word-for-word what a spoken reminder earns, so a typed reminder behaves identically to a said one. No confirmation card and no gate, the ADR 0025 stance a spoken one takes: the sentence IS the authorisation and a wrong reminder is undone with one cancel. A refusal is `-32001` with field-keyed `problems` (`when` for an unreadable time, `text` for empty words), nothing written. Publishes `reminders.changed` |
| `config.upsert_entry` | `{family, name?, entry, secrets?, fingerprint?}` | `{fingerprint, applied, created, reason?}` | Writes one whole entry (#99): create (empty `name`) appends the rendered table at the end of config.toml; edit replaces exactly the named entry's block in place (rename allowed) — comments, sibling entries, and unrelated `[[routines.steps]]` sub-tables byte-preserved by the same editor discipline as `automations.set_enabled`. The pipeline is validate-whole-then-write: the exact `config.validate_entry` check runs first, and a failure is a `-32001` refusal carrying the field-keyed `problems` with NOTHING written — never a half-write. A stale `fingerprint` (the file changed outside the window since the form opened) is a `-32002` conflict carrying the fresh one, nothing written. On success the write is atomic, the standard reload recompiles the grammar and rebuilds the schedules, `config.changed` fires, and the activity feed carries a row naming the entry. Saving is not an execution path: nothing runs. For a keyed family (`ai`, `advisors`) create places the new `[family.<name>]` table after the last existing one so the section stays together, and edit rewrites the header on a rename. A `keep` credential instruction (the default) is honoured by reading the stored value out of the file and writing it back — it exists nowhere in between — and every problem, error and reason on this path is scrubbed of the values in play (ADR 0052) |
| `config.delete_entry` | `{family, name, fingerprint?}` | `{fingerprint, applied, reason?}` | Removes one entry whole (#99): its block, its sub-tables, and the comment glued to its header (a comment separated by a blank line — a section header — stays), everything else byte-preserved. Same guards as `config.upsert_entry`: fingerprint conflict is `-32002`, a removal the whole-document validation refuses is `-32001` with the problems, and only a valid result is written (atomic) and applied by the standard reload — phrases leave the grammar, the schedule stops. The activity feed carries a row naming the deleted entry — the fact that a provider was edited, never what changed. A family may also declare an in-use guard that refuses first with its own reason: deleting the `[ai.<name>]` table `ai.provider` currently names is a `-32001` saying so, because a deleted PRESET endpoint would still validate while leaving the user pointing at something they can no longer see |
| `config.list_entries` | `{family}` | `{fingerprint, family, kind, entries, in_use?}` | Every entry of one family, from the file, in the same secret-stripped shape `config.get_entry` returns one (#163). The families are `routines`, `scripts`, `knowledge.feeds`, `ai`, `advisors`, `intents.custom` and `tts.lexicon`. Registry-driven rather than summarised per family: each row is `{entry, secrets?, notes?}` and a listing screen renders whichever keys it has widgets for, so a family added to the registry needs no listing code. Order is document order for array families and sorted for keyed ones — the order each shape can promise. `in_use` accompanies `ai` only: the endpoint `ai.provider` currently names, so a row can say so and a delete button can explain itself before it is pressed |
| `config.test_entry` | `{family, name}` | `{family, name, outcome, summary, base_url?, status?, detail?, secrets?}` | The family's live probe against the entry AS SAVED (#163, on #114's real-probe discipline). For `ai` that is `GET {base_url}/models` with the credential resolved daemon-side — the cheapest request that proves both halves, since it costs no tokens and returns 401 rather than 200 for a wrong key — bounded by a ten-second budget. `outcome` is `reachable` (a 2xx that actually arrived), `unauthorised` (401/402/403 — the URL is right, the key is not), or `unreachable` (a refused dial, a timeout, or a status meaning this is not an API root). `detail` is the service's OWN error text or the transport's, truncated, never a guess and never the credential; `summary` is the one sentence saying what to do next. A success is never fabricated: nothing but a real 2xx reports reachable. A family with no probe is refused (`-32602`) rather than answered |
| `doctor.get` | — | `{checks}` | The settings-relevant readiness subset of `jarvix doctor` — offline and fast (no provider probe, no audio round trips). Each check: `status` (`ok`/`warn`/`fail`), `name`, `detail`, `fix`, and `related` — the config key the check informs, so a settings screen can show readiness inline |
| `state.hold` | `{ttl_ms?}` | `{held, ttl_ms}` | Backup consistency barrier (ADR 0045): drains in-flight store writes, then blocks new ones until `state.release` or the TTL (default 10s, max 60s) — whichever first. The reply arriving IS the guarantee: from that moment the state root is a coherent point in time for `jarvix backup` to copy. One hold at a time; a second is refused (`-32600`) — one backup at a time. The TTL is the safety net for a backup process that dies mid-copy: the daemon always reopens on its own |
| `state.release` | — | `{held: false}` | Reopens the barrier. Idempotent — releasing after the TTL already fired answers the same, because the caller's question is "may writes flow again?". Works from any connection, not just the holder's, so a crashed backup can be released by hand |

Errors use JSON-RPC error objects. Application errors (wrong state, no active
session) use code `-32000`; standard codes cover parse/method/params issues.
The config surface adds three codes, each with structured `data`:

| Code | Meaning | `data` |
|---|---|---|
| `-32001` | config.set/reload rejected by validation; nothing written/applied | `{problems: [...]}` — `config.Validate` messages, each prefixed with the offending key |
| `-32002` | config.toml changed on disk since the client's `config.get`; nothing written | `{fingerprint}` — the file as it is now; re-read and reapply |
| `-32003` | config.reload could not apply because a session is active; running config unchanged | — |

### Example

```text
→ {"jsonrpc":"2.0","id":1,"method":"session.start"}
← {"jsonrpc":"2.0","id":1,"result":{"session_id":"s7"}}
→ {"jsonrpc":"2.0","id":2,"method":"session.submit","params":{"text":"hello"}}
← {"jsonrpc":"2.0","id":2,"result":{}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"thinking","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"assistant.started","params":{"session_id":"s7","provider":"ollama"}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"responding","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"assistant.delta","params":{"session_id":"s7","content":"Hi"}}
← {"jsonrpc":"2.0","method":"assistant.delta","params":{"session_id":"s7","content":" there."}}
← {"jsonrpc":"2.0","method":"assistant.finished","params":{"session_id":"s7","content":"Hi there."}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"speaking","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"tts.started","params":{"session_id":"s7"}}
← {"jsonrpc":"2.0","method":"tts.finished","params":{"session_id":"s7"}}
← {"jsonrpc":"2.0","method":"state.changed","params":{"state":"idle","session_id":"s7"}}
← {"jsonrpc":"2.0","method":"session.finished","params":{"session_id":"s7"}}
```

Try it by hand:

```bash
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"status.get"}' | nc -U "$XDG_RUNTIME_DIR/jarvix.sock"
```

## Events

Every event's params include `session_id` where a session is involved.

| Event | Params | Meaning |
|---|---|---|
| `state.changed` | `{state, session_id, since_ms}` | Authoritative state transition. `since_ms` is when this state began, as Unix milliseconds on the daemon's clock (issue #158): every surface that says how long a wait has run counts from it, so the bar, the window, and a window opened halfway through agree. Counting from when a client *noticed* the transition is right only for a client that was already watching |
| `recording.started` / `recording.stopped` | `{session_id}` | Microphone capture bounds |
| `transcript.partial` | `{text}` | Interim hypothesis (reserved; whisper.cpp V1 emits none) |
| `transcript.final` | `{text}` | Completed transcript |
| `context.captured` | `{sources, duration_ms}` | Desktop context was gathered for this turn (ADR 0019), immediately before the provider request. `sources` is an array of `{source, chars, truncated, redacted}` — **sizes and flags only, never content**, because events fan out to every connected client. Published only on turns that reach the model: a matched deterministic intent gathers nothing. Fetch the captured text itself with `context.last` |
| `knowledge.injected` | `{feeds, trimmed, est_tokens}` | Cached feed values were offered to the model for this turn (ADR 0031), beside the desktop context. **Counts and estimates only, never values** — feed values may be sensitive; they are fetched with `knowledge.status`, over the socket, on request. Published only on turns that reach the model, and only when at least one opted-in feed had a value |
| `knowledge.updated` | `{feed}` | A fetch attempt for this feed completed — scheduled or `knowledge.refresh_now`, success or failure — so an open Knowledge tab re-requests `knowledge.status`. **Name only, never the value or the error**: those ride the status reply, over the socket, on request |
| `memory.injected` | `{facts, trimmed, searchable, total, est_tokens}` | Remembered facts were offered to the model for this turn (ADR 0025), immediately before the provider request; `searchable` counts the facts deliberately behind `memory.search` under ADR 0037's split. **Counts and estimates only, never content** — fact text is fetched with `memory.last`, over the socket, on request. Published only on turns that reach the model, and only with memory enabled |
| `memory.entry_changed` | `{action, id, chars}` | A fact was added, edited, pinned, or unpinned through the window (`memory.add` / `memory.update` / `memory.set_pinned`, #100/#104), so an open Memory tab re-requests `memory.list`. **Id and size only, never the words** — content travels over the socket, on request, like every other memory surface |
| `vocabulary.injected` | `{entries, trimmed, total, est_tokens}` | Taught words were offered to the model for this turn (issue #129), beside the remembered facts. **Counts and estimates only, never phrases** — content is fetched with `vocabulary.last`, over the socket, on request. Published only on turns that reach the model, and only with vocabulary enabled |
| `vocabulary.entry_changed` | `{action, id, chars}` | A word was `taught`, `edited`, `flagged`, or `forgotten` — through the window's form, a spoken "when I say X I mean Y", or the model's `vocabulary.teach` — so an open Vocabulary section re-requests `vocabulary.list`. **Id and size only, never the words** — the memory privacy contract, held for vocabulary verbatim |
| `config.entry_changed` | `{action, family, kind, name, source}` | One `[[family]]` entry was created, edited, or deleted through the entry verbs — the window's forms (#99/#100) or the assistant's config tools (#105); `source` (`window` \| `assistant`) says which, and the activity row words it ("saved from the window" / "saved by the assistant"). Listings refresh off the accompanying `config.changed` |
| `config.setting_changed` | `{key, source}` | One registry setting changed through `config.set` — the settings screen or CLI (`source: user`) or the assistant's `config.write_setting` tool (`source: assistant`, #105). One event per changed key, in sorted order, after the accompanying `config.changed`. **Key and source only, never the value** — a value can be a whole system prompt; values travel over `config.get`, on request |
| `assistant.started` | `{provider}` | Provider request opened |
| `assistant.delta` | `{content}` | One streamed response fragment |
| `assistant.finished` | `{content, tool_calls}` | Full response text. `tool_calls` counts the tool calls the model requested this turn — attempts, including denied and declined ones. Zero on an answer that claims action is the model narrating work it never asked to do, which is exactly what the activity feed's text-only marker makes visible |
| `tool.started` / `tool.finished` | `{tool, arguments, detail?}` / `{tool, duration_ms, outcome}` | Bounds of one real tool execution — never published for denied or declined calls. `detail` is present only for tools that can run long (an advisor consultation) and is a short label to show for the duration, e.g. `Consulting claude…`. `outcome` is `ok`, or `error` for the registry's own failures (unknown tool, infrastructure err) — the one failure shape this layer can attest to; a tool that ran and refused reports its reason in its own audit events (`typing.audit`, `desktop.refusal`) |
| `tool.progress` | `{tool, message, elapsed_sec}` | A tool has been running for `elapsed_sec` seconds and is still going. Published **at most once** per call, and only for tools that carry a `detail` label; `message` is also spoken aloud. Reassurance, not a countdown — clients should show it and expect nothing further until `tool.finished` |
| `tool.confirmation_required` | `{tool, command, summary, rule, timeout_sec, remember_pattern?, remember_segment?, remember_reason?}` | The permission gate paused a tool call (state `awaiting_confirmation`). `command` is the exact command, verbatim; `summary` is the full one-sentence question, generated daemon-side from the command — always carried here whatever is spoken: by default the daemon speaks a short prompt naming the action class ("May I run a shell command? The details are on screen."), and `confirmations.speak_details = true` speaks this summary verbatim instead (issue #119; ADR 0014 as amended). The conversation window's confirmation card displays `command` **verbatim** — clients must never summarise or re-derive it (ADR 0014); the mid-screen overlay shows `summary` compactly with approve/decline controls and defers to the card for the verbatim text. For `advisor.ask`, `command` is the advisor's name — what the user is actually approving, and what a remembered approval is keyed on. The remember offer (#162, ADR 0053) rides this event so the card can show the third button with its exact rule on it before the user commits: exactly one of `remember_pattern` (the word-prefix `session.confirm {remember}` would add, verbatim, with `remember_segment` the part of a compound it came from) and `remember_reason` (one short sentence saying why no rule is offered) is present, and their presence is the fact — a card with neither shows only approve and decline |
| `tool.pre_approved` | `{tool, command, rule, pattern?, scope}` | A command ran **without being asked about** because a rule the user granted allowed it (#162, ADR 0053) — a `[tools.policy] shell_allow` pattern, a conversation-scoped grant, or `remember_for_conversation`'s remembered approval. `rule` names what let it through and `pattern` is the word-prefix itself; `scope` is `always` or `conversation`. Published before the tool runs, and rendered by the activity feed as "Ran without asking: …", because a standing grant removes the *question* and must not also remove the evidence. Shipped read-only allow patterns (`ls`, `git status`) do not publish it: they are not grants anybody made |
| `approvals.changed` | `{action, pattern, list, scope?, source}` | A rule in `[tools.policy]` was added or removed outside a confirmation card — the CLI, or the window's Approvals view. `action` is `added` or `forgotten`, `list` is `allow` or `deny` (#164), and `source` is `card`, `cli`, or `window`. Pattern only; the pattern *is* the permission, so there is nothing here to withhold |
| `tool.confirmation_deadline` | `{tool, command, deadline_ms, timeout_sec}` | The confirmation countdown started: the pending call auto-declines at `deadline_ms` (Unix milliseconds). A separate event because the clock starts only once the question has been *asked* — `tool.confirmation_required` goes out before the question is spoken, so it cannot honestly carry a deadline. Clients derive the countdown from `deadline_ms`, never from a hardcoded timeout; until this event arrives, `timeout_sec` from `confirmation_required` is the most that can be said. Not published when the confirmation resolved while the question was still being spoken |
| `tool.confirmed` | `{tool, command, source}` | The user approved; the call executes. `source`: `cli`, `text`, or `voice` |
| `tool.declined` | `{tool, command, source}` | The call will not run. `source`: `cli`, `text`, `voice`, `timeout`, `interrupted`, or `error` |
| `tool.denied` | `{tool, command, rule}` | A deny rule blocked the call outright; no confirmation is possible |
| `typing.audit` | `{tool, window, chars, approved, terminal, outcome, key?, reason?}` | Jarvix made a typing decision (ADR 0023). `outcome` is `typed`, `pressed`, `refused`, `focus-changed`, or `unavailable`; `approved` says whether a human confirmed this exact action rather than the configured tier allowing it; `terminal` marks a target whose contents are a command line. **The typed text is never published**: the payload may be a password the user dictated, and a bus event reaches every subscriber. `chars` is how many characters, never which. The daemon retains the most recent one for `jarvix status --last` |
| `desktop.action` | `{verb, target}` | Jarvix acted on the desktop (ADR 0022). `verb` is `focus`, `move`, `close`, `launch`, `list`, or `name` (#126 — `target` then carries the window and its new nickname, `firefox — GitHub → mail`); `target` names the window as a person would (`firefox — GitHub`) or the application started. Published after the action succeeded, so it is a record of what happened, not what was attempted. Window addresses are never published: they are compositor internals and nothing spoken or shown needs them |
| `desktop.refusal` | `{verb, target, reason}` | Jarvix tried to act on the desktop and could not (issue #70): a launch the resolver refused (`launch` / `firefox` / `it is not installed`), a launch that failed to start, a dispatch the compositor rejected. `reason` is composed to be safe on the bus — the resolver's own spoken-form sentence, or a generic clause where the underlying error is operator material (launcher errors, compositor diagnostics, which stay in the journal). Window addresses never travel, same as `desktop.action` |
| `activity.row` | `{seq, ts, session_id, kind, label, detail, failed}` | One rendered activity-feed row, pushed as it is appended to the ring — the live half of `activity.get`, same shape, merged by `seq`. Derived by the daemon's own feed subscriber from the event that caused it, so it may trail that event on the wire (see ordering below). Clients render it verbatim; the wording is decided and tested daemon-side |
| `intent.executed` | `{intent, source, status, acknowledgement, duration_ms, slot?, routine?, script?, error?}` | The deterministic intent router handled the utterance locally, with no provider request (ADR 0017). `intent` is the id (`volume.set`, `speech.stop`, `custom.lock the screen`); `source` is `builtin`, `user`, `routine`, or `script` (with `routine`/`script` naming which — ADR 0026/0030; a layout capture, #62, reports `intent: routine.capture` with `routine` naming the saved entry); `status` is `ok` or `failed` (with `error` when the command failed, was declined, or was denied); `slot` is the validated integer for intents that take one; `duration_ms` is measured from the final transcript. `acknowledgement` is what Jarvix says — flash it in the overlay; it is empty for `speech.stop`, where silence is the confirmation |
| `routine.started` | `{routine, steps}` | A routine began executing (ADR 0026): its name and how many steps it will run |
| `routine.step` | `{routine, step, app, workspace, launched, status, detail?}` | One step finished: `step` counts from 1, `launched` distinguishes a fresh launch from a deduped existing window, `status` is `placed` or `failed` (with `detail` naming why). Progress for the bar and the window — the user only ever *hears* the final summary |
| `routine.finished` | `{routine, placed, failed, failures, summary, duration_ms}` | The routine completed: how many steps landed, the failure clauses, the summary sentence that was spoken, and how long the run took (#93 — the Automations tab's last-run line words the same number the log reports). Not published for a cancelled run — `session.cancelled` owns that ending |
| `script.started` | `{script, path}` | A configured script began executing (ADR 0030): its name and the exact file being run — the same path the gate's confirmation named, repeated on the audit surface. Never the script's output, in this event or any other |
| `script.finished` | `{script, path, status, exit_code, timed_out, duration_ms}` | The script ended: `status` is `ok` or `failed`, with the exit code and duration always present — success included, so "did my backup actually run?" is answerable from the feed. Not published for a cancelled run — `session.cancelled` owns that ending. Output (stdout/stderr) is deliberately absent: it can contain anything the script read, and events fan out to every connected client |
| `automation.fired` | `{kind, name, schedule, announce}` | A schedule fired (ADR 0032): the clock, not a person, started what follows. The run itself reports through the ordinary events above — the session it starts is a normal session, quiet unless `announce` is true |
| `automation.skipped` | `{kind, name, schedule, reason}` | A scheduled firing did not run, with the reason: the previous run was still going (a schedule is not a queue), or a conversation was active (the clock never interrupts a person). Reported so a skipped firing is a row, never a silence |
| `automation.refused` | `{kind, name, schedule, reason, rule}` | A scheduled firing of an entry whose tier is anything short of allow: nothing executed — a schedule cannot answer a confirmation question — and the deciding policy `rule` is on the record. Accompanied by a desktop notification whose click opens the window |
| `automation.missed` | `{kind, name, schedule, due}` | Boot found a firing that fell while no daemon was running: reported once, with when it was due (RFC 3339) — and never re-fired, because the daemon cannot know whether 3am's intent still holds at 9am. Say the phrase to run it now |
| `focus.changed` | `{reason, active, active_name?, session, thread?, minutes?}` | The focus-thread store changed (#123, ADR 0041): `reason` is `created`, `switched`, `parked`, `anchored`, `ended`, `session_started`, `session_closing`, `session_ended`, `reminder_set`, or `reminder_cleared`. `active` is the active thread's id (`""` when none), `active_name` its name, and `session` whether a timeboxed focus session is live — carried on every one of these events so the bar/overlay siblings (#124/#127) can show the current context from the event alone, no round trip. Open Focus tabs re-request `focus.list` rather than guessing what the change meant. Parked-thought text never travels here — content rides `focus.list`, over the socket, on request |
| `focus.recap` | `{thread, name, outcome, source, chars, capture_ms, model_ms, total_ms, session_state?}` | An AI-session recap was attempted (#124, ADR 0042): `outcome` is `spoken` (the model's summary was spoken), `capture_failed` (the anchored window could not be read; the thread's own record spoke behind the pinned admission), or `model_failed` (no usable summary inside the deadline; same fallback). `source` names the capture layer that served (#137, ADR 0047): `transcript` (the session's own transcript tail) or `title` (the window identity line — including when a discovered transcript could not be read and the recap admitted the downgrade). `session_state`, when present, is the deterministic `working` / `needs_you` / `done` classification read from the transcript's structure — the same field `focus.list` carries for the overlay dot (#127), absent when unknown. Sizes and outcomes only, and that is the whole point: the captured content and the summary are transient — spoken, never stored — so this event is how the activity ring says a recap happened without repeating what it said, and how the latency budget is measured |
| `focus.skipped` | `{kind, thread, reason}` | A scheduled focus moment — a check-in reminder, a timebox midpoint or close — was not spoken, with the reason: a session was live or speech was playing (the do-not-nag rule, ADR 0041). Dropped, never queued: the next moment is computed from the schedule, so skips can never pour out as a backlog. The state the firing would have announced was already recorded before the attempt, so nothing is lost but the sentence |
| `overlays.changed` | `{rows}` | The window-overlay feed's rows changed (#127): the same row shape `overlays.get` serves, published wholesale — every publication is the complete current surface, so a client renders what arrived and never reconciles deltas. Published only on change: geometry is polled gently daemon-side (every 2s while anything is enrolled, parked entirely otherwise — ADR 0044 records why polling), so a quiet desktop costs no traffic, a moved or closed window converges within a poll, and an empty `rows` means "clear everything" (overlays disabled, nothing enrolled, a fullscreen workspace, or an unreadable compositor — all rendered identically as absence) |
| `reminders.changed` | `{reason, id?, count?}` | The one-shot reminder store changed (#141, ADR 0046): `reason` is `created`, `cancelled`, `fired`, or `deferred`. `id` names the reminder for the first two; `count` carries how many were delivered (`fired`) or held (`deferred`). A `deferred` event is the do-not-nag rule doing its job — the moment arrived while a session was live or speech was playing, so the reminder is **owed**, not dropped: it is parked and delivered at that session's end, marked late in the spoken line once past two minutes. Reminder text never travels here — content rides `reminders.list`, over the socket, on request. Open Automations tabs re-request rather than guessing what the change meant |
| `briefing.given` | `{reason, lines, sections, truncated, empty, partial, model, away, unavailable?}` | A return briefing was given (#150, ADR 0050) — the activity feed's row is built from this, and from nothing else. `reason` is `ask` (a spoken phrase or the model's tool), `return` (`briefing.speak_on_return` spoke it unprompted), or `window` (the Focus tab's button). `lines` and `sections` are how much was said, `truncated` whether the spoken form was shortened for speech, `empty` whether the honest answer was "nothing since you were last here", `partial` whether the window opened before the daemon started and so could not be fully accounted for (#190), `model` the headline's outcome (`used`, `refused`, or `off`), `away` the spoken-style age of the window, and `unavailable` a comma-separated list of source names that could not be read. **Not one word of the briefing travels here** — the composed account exists in the spoken sentence and nowhere else: it is written to no store, added to no conversation memory, and a leak-salted test fails the build if content reaches this event or the row built from it |
| `wake.detected` | `{confidence}` | The wake word was recognised and a session is starting (ADR 0024). Published **before** transcription, so the overlay can acknowledge the wake word while whisper is still working. It carries a confidence and nothing else — never audio, never text: events fan out to every connected client, and pre-wake audio does not leave the daemon |
| `wake.changed` | `{state}` | What the microphone indicator should show: `off` (nothing is capturing), `armed` (a capture process is running), or `muted` (`jarvix mute` is in force). A second dimension alongside `state.changed` rather than another session state — a session state describes a turn, this describes the microphone between turns |
| `tts.started` / `tts.finished` | `{}`; finished may carry `{interrupted:true}` | Speech bounds. Exactly one pair per answer that starts speaking, however many sentences supersession drops in between — a superseded queue never splits or doubles the bookends |
| `speech.replayed` | `{session_id, turn, role}` | A `speech.replay` finished speaking a recorded turn whole (issue #122): which conversation.get position was spoken again, and its role. Published before the replay session's `session.finished`; the activity feed's "Spoke turn N again" row is derived from it. Not published for a replay that was cancelled or superseded — `session.cancelled` owns that ending, exactly as for routines and scripts |
| `tts.superseded` | `{turn, dropped}` | Queued speech from an earlier turn was dropped unplayed because a newer turn committed speech (issue #120): playback jumps to the conversation's leading edge instead of reading stale narration. `turn` is the speaker-internal ordinal of the turn that won (1 is the answer's first provider round); `dropped` is how many queued sentences were skipped — one event per catch-up, published as the first surviving sentence is reached. **Audio only**: the transcript, `assistant.delta`, and the record carried every dropped sentence when it streamed. Confirmation questions are never dropped (they gate progress); the session's `session.timings` carries the turn total as `superseded_sentences` |
| `session.timings` | `{capture_to_transcript_ms?, context_ms?, transcript_to_first_delta_ms?, first_delta_to_first_pcm_ms?, first_pcm_to_audio_out_ms?, tool_ms?, confirm_wait_ms?, release_to_first_audio_ms?, jarvix_ms?, superseded_sentences?}` | The session's latency budget, published immediately before `session.finished` (ADR 0018). `superseded_sentences` is the one non-duration key — how many queued sentences supersession dropped unplayed this turn (issue #120), present only when the count is non-zero. Each key is a completed stage in milliseconds; **a stage that did not happen is absent, not zero** — a typed question has no capture stage, a silent answer has no audio stages, and a turn with desktop context disabled has no `context_ms`. `context_ms` is desktop-context gathering (ADR 0019), which sits between the transcript and the request: the model's clock starts where it stops, so gathering is counted in `jarvix_ms` rather than excused as thinking time. `transcript_to_first_delta_ms` is the model's time to its first output — a text token or a tool call — which is the user's choice of model, not Jarvix's latency. `tool_ms` (time inside tool executions) and `confirm_wait_ms` (time waiting on the user's confirmation answer) are the turn's **excluded spans** (issue #72): reported so the turn's real length is on the record, attributed to neither Jarvix nor the model, and subtracted from any pipeline stage they fell inside. `jarvix_ms` is `release_to_first_audio_ms` minus thinking minus the excluded time before the first sound — the number Jarvix is accountable for, **non-negative by construction** (every stage is; a span whose accounting cannot be reconciled is dropped rather than published negative). Also emitted as one structured log line with identical keys |
| `session.finished` | `{}` | Session completed (also after an error) |
| `session.cancelled` | `{reason}` | Session cancelled or interrupted. The exchange the session was carrying — the user's turn and any partial answer — is committed to working memory and the archive **marked interrupted** before this event is published (issue #117), so a `conversation.*` read issued after seeing it already finds the exchange (the same read-your-acknowledged-writes barrier `session.finished` gets). A session cancelled before it had a transcript commits nothing — there is no exchange to keep |
| `error` | `{stage, message}` | A stage failed: `audio`, `stt`, `assistant`, `tts`, `session` |
| `config.changed` | `{fingerprint}` | Configuration was saved (`config.set`) or reloaded; open settings views should refresh via `config.get` |
| `conversation.changed` | `{reason, conversation_id?}` | The live thread changed underneath open views: `reset` (`jarvix new`, a delete of the active conversation) or `opened` (an archived conversation was reopened, ADR 0027). Re-request `conversation.get` rather than guessing what the change meant |

States seen in `state.changed`: `idle`, `listening`, `transcribing`,
`thinking`, `responding`, `awaiting_confirmation`, `acting`, `speaking`,
`cancelling`, `error`. `acting` is a deterministic local action — a matched
intent, or a `speech.replay` re-reading a recorded turn — and never passes
through `thinking`/`responding`, because no provider request is open.

Ordering guarantees: `state.changed` precedes the stage events it enables;
`session.timings` immediately precedes `session.finished`; and
`session.finished`/`session.cancelled` is always the last *engine* event of a
session. `activity.row` is exempt from that last clause: it is derived — the
daemon's feed subscriber rendering engine events it has just received — so a
row for a session's final events can arrive shortly after `session.finished`.
Rows do preserve their own order (`seq`), and a client that treats
`session.finished` as terminal loses nothing: `activity.get` reconciles.
Slow consumers may lose events (the daemon never blocks on a client), so the
overlay treats `state.changed` as the source of truth and resyncs with
`status.get` on reconnect.

## The shell plugin's own IPC surface

Separate from the daemon socket above: the Omarchy shell exposes each
plugin's `IpcHandler` through `omarchy-shell <target> <function>`. Jarvix
registers two targets, and this is how the CLI, notifications, and the bar
widget reach the plugin's windows without the daemon being involved — which
matters, because the window and the widget must work with jarvixd stopped.

| Target | Function | Effect |
|---|---|---|
| `jarvix` | `openWindow` / `closeWindow` / `toggleWindow` | Show, hide, or toggle the conversation window. `jarvix window`, a clicked notification, and the bar widget all go through here — there is only ever one window. A compositor-killed window (super+W) is rebuilt on the next open rather than re-shown; `scripts/verify-window-kill.sh` checks that live (issue #106) |
| `jarvix` | `openSettings` | Open the window already showing the Settings tab (the bar widget's Settings action) |
| `jarvix` | `state` / `ping` | The overlay's view of the session state; liveness |
| `jarvix.bar` | `open` / `close` / `toggle` / `show` / `hide` | The bar widget's panel |
| `jarvix.bar` | `state` | The state key the bar icon is showing — one of the daemon states above, or `not-running`, `error`, or `working` (an unrecognised state), or `wake-armed` / `wake-muted` when the daemon is idle and background listening is on. `scripts/verify-bar-widget.sh` reads this to check the icon against the daemon |

The widget's own vocabulary — the glyph, words, and urgency for each state —
is defined in `internal/desktop/barstatus.go` and generated into
`plugin/omarchy/BarState.js`; see [ADR 0020](adr/0020-bar-widget-not-tray-icon.md).
The same arrangement covers the activity feed: row wording lives in
`internal/desktop/activity.go` (rows arrive from the daemon already
rendered), and the window's glyph-per-kind table is generated into
`plugin/omarchy/ActivityState.js`.
